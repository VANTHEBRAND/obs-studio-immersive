# Control All of OBS From Vision Pro

The product that fits the evidence is a **native SwiftUI/RealityKit visionOS app that contains no libobs**, speaks obs-websocket to an OBS Studio running on a Mac, receives Program, Preview and any other network feed as **NDI through the outputs DistroAV already provides**, and closes the gap between "scene switcher" and "full control parity" with one small companion plugin in this fork that extends obs-websocket with vendor requests. Nobody has shipped a native OBS client for visionOS: the four OBS remotes that run on Vision Pro today are iPad apps in compatibility mode, and the closest template, ProducerPad, already pairs websocket control with NDI monitoring. obs-websocket carries no video by maintainer decision, which is why video comes from a separate output, and NDI's SDK has supported visionOS since 6.2, so no new video code is needed on either end. The Mac host stays stock: OBS 32.2.2 (33.0 at RC3) with bundled obs-websocket 5.7.x, DistroAV and NDI Runtime 6.3+, plus the companion plugin, which the OBS 33 plugin-loader overhaul leaves untouched on macOS. Parity means everything the desktop app can do, sorted into four tiers: what the protocol already exposes, what vendor requests add, the Settings dialog's apply semantics (the main upstream-sync risk, scoped to output, video and audio first), and desktop-app-level features such as plugin installation, the auto-config wizard and chat docks, each reachable from the headset. Input is gaze-and-pinch, with PSVR2 Sense controllers optional and never required. Apple's `RemoteImmersiveSpace` becomes a later optional "immersive studio" mode because it is Metal-only, full or progressive immersion only, hides every other app and first shipped in macOS 26; Mac Virtual Display is never a dependency. The two concentrated risks are Wi-Fi 6 bandwidth for NDI on the headset, which Phase 0 measures before anything is built on it, and the settings apply logic, the one place the headset must mirror frontend code that upstream keeps changing.

A note on sourcing: most facts below come from primary pages read directly (Apple developer and support pages, OBS documentation and site, the App Store, NDI's SDK docs, the obs-websocket header and server source, and this checkout) and are cited inline. What remains unverified from a primary source is listed in the open-questions table; the main items are Apple's Developer Strap page (behind a sign-in, so its price and bandwidth are press-sourced), any Apple or NDI latency figure for the transports discussed, Apple's own position on GPL apps in the App Store (moot for a client that contains no GPL code), LiveKit's official visionOS limitations page, and NDI's marketing platform list, which still omits visionOS even though the SDK release notes include it. Strategy decisions made by the project owner are marked as project decisions, not research findings. A Qt-based cross-platform approach was evaluated in the [earlier report](<docs/immersive/reports/OBS immersive XR port research.md>) and dropped in favour of a native visionOS app; where the desktop frontend's internals matter below (settings apply logic, dock configuration, cookie stores) it is referred to simply as the desktop frontend.

## No native OBS client exists for visionOS; ProducerPad is the closest template, and obs-websocket will never carry video

The OBS forum's own search returns **"No results found."** for "Vision Pro" and "visionOS", and the project's GitHub Discussions return "There are no matching discussions" for "vision pro" ([OBS forum search](https://obsproject.com/forum/search/search?keywords=%22Vision+Pro%22); [Discussions](https://github.com/obsproject/obs-studio/discussions?discussions_q=vision+pro)). A native, spatial OBS client would be the first of its kind, and the team should expect no reusable visionOS-specific OBS code.

What does exist on Vision Pro is the iPad obs-websocket remote, and direct reads of the US App Store show **four of the five** apps checked list "Apple Vision" compatibility, all as "Designed for iPad" apps and none as a native visionOS build. OBS Controller ($1.99, visionOS 1.0 or later, v0.11.0 of 13 January 2026) calls itself "a simple mobile scene switcher" with no video ([App Store](https://apps.apple.com/us/app/obs-controller/id1547228500)). OBS Blade (free, GPL-3.0 Flutter, visionOS 1.0 or later, v4.2.0 of 21 October 2026) advertises a "live scene preview" ([App Store](https://apps.apple.com/us/app/obs-blade/id1523915884)). CTD Live Mobile ($1.99, visionOS 26.0 or later) confirms how such previews are built, per-pane `GetSourceScreenshot` polling: "The app now asks OBS for the size each pane will really be drawn at" ([App Store](https://apps.apple.com/us/app/ctd-live-mobile/id6780304134)). **ProducerPad** (iOS 18, visionOS 2.0 or later) is the design template for this project: "Monitor Program and Preview with ProducerPad Feed or NDI on supported setups", where "NDI monitoring requires a compatible NDI setup", plus scene switching, a VU-meter mixer, remote text-source editing and QR-code pairing on the same LAN ([App Store](https://apps.apple.com/us/app/producerpad/id6755590424); [OBS forum resource](https://obsproject.com/forum/resources/producer-pad.2316/)). Touch Portal lists no Apple Vision line ([App Store](https://apps.apple.com/us/app/touch-portal/id1410172542)). Because "runs on Vision Pro" is the default for iPad apps unless the developer opts out, the Apple Vision line is weak evidence of intent, and none of these is more than a switcher with thumbnails; the owner's parity goal is a different product category. The one open-source Swift obs-websocket v5 library, OBSwiftSocket, is "currently on pause... mostly works, but has some issues" per its author ([Swift Package Index](https://swiftpackageindex.com/edonv/OBSwiftSocket)), so the client should expect to own its protocol layer.

The control-versus-video split is forced by the protocol. OBS 32.2.2 bundles obs-websocket **5.7.4** and OBS 33.0-rc3 (and this tree) bundle **5.7.6**, both rpcVersion 1 ([CMakeLists at 32.2.2's pin](https://raw.githubusercontent.com/obsproject/obs-websocket/1ef34bf48110c2a18184e50e41cd0b1a855e2147/CMakeLists.txt); [CMakeLists at 33.0-rc3's pin](https://raw.githubusercontent.com/obsproject/obs-websocket/e28f84975984340e84fc4879cfc05741cc0afde1/CMakeLists.txt)). The protocol's only image facility is `GetSourceScreenshot`, a base64 image per call sized 8 to 4096 px, and a grep of the generated protocol document for "video stream", "frame stream" or "continuous" returns nothing ([protocol.md](https://raw.githubusercontent.com/obsproject/obs-websocket/master/docs/generated/protocol.md)). That is policy: issue #545 asked in June 2020 for a websocket video stream so OBS-web could show Program and Preview, and maintainer tt2468 closed it as not "worth the incredible amount of work", adding that it "is out of the scope of obs-websocket" and belongs in its own plugin ([obs-websocket #545](https://github.com/obsproject/obs-websocket/issues/545)). Five years later the only movement is a stalled single-frame `GetStreamScreenshot` PR, an unanswered request for dedicated Program and Preview screenshots, and an unconfirmed bug that `GetSourceScreenshot` returns the preview rather than the program in some Studio Mode cases ([PR #1189](https://github.com/obsproject/obs-websocket/pull/1189); [#1130](https://github.com/obsproject/obs-websocket/issues/1130); [#1257](https://github.com/obsproject/obs-websocket/issues/1257)). Video therefore comes from a separate output, which is what DistroAV provides and what the owner has chosen; screenshot polling stays useful only for low-rate thumbnails, and even there the client must screenshot the program scene by UUID rather than trust "current" during Studio Mode edits.

## visionOS gives a remote client windows, volumes, gaze-and-pinch and an NDI receiver, but not background execution

The window rules favour a native app. An app that sets `UIApplicationSupportsMultipleScenes` "can display any number of windows together with an immersive space"; only one immersive space may be open system-wide, and opening one "hides all windows that belong to other apps", with the converse also true ([Presenting windows and spaces](https://developer.apple.com/documentation/visionos/presenting-windows-and-spaces)). Apple publishes no numeric cap on windows. A SwiftUI app can therefore float a scenes panel, a mixer, a transport strip, generated settings forms and video windows in the Shared Space, add a volume for a multiview wall, and offer an optional immersive stage, with the operator's other apps still visible until the stage is opened; only a native app living in the Shared Space can have this layout.

Input anchors the project's input model. Apple's M5 tech specs list "Supported Input Accessories: Keyboards; Trackpads and mouse devices (Mouse support requires visionOS 2 or later); Game controllers" and "Supported Spatial Accessories: Logitech Muse; PlayStation VR2 Sense controller", with the primary inputs "Hands, Eyes, Voice" ([Apple Support 125436](https://support.apple.com/en-us/125436)). visionOS 26 introduced the Sense controller with "high-performance motion tracking in 6 degrees of freedom, finger touch detection, and vibration support", sold by Apple from 11 November 2025 at $249.95 ([Apple Newsroom, June 2025](https://www.apple.com/newsroom/2025/06/visionos-26-introduces-powerful-new-spatial-experiences-for-apple-vision-pro/); [Apple Newsroom, October 2025](https://www.apple.com/newsroom/2025/10/apple-vision-pro-upgraded-with-the-m5-chip-and-dual-knit-band/)). visionOS 27 adds custom tracked accessories through the Game Controller framework and tracks hands at 90 Hz ([WWDC26 287](https://developer.apple.com/videos/play/wwdc2026/287/)), and a visionOS 26 release note records that while a controller is tracked, ARKit hand tracking for that hand updated at only 1 Hz until fixed ([visionOS 26 Release Notes](https://developer.apple.com/documentation/visionos-release-notes/visionos-26-release-notes)). The project decision is that **gaze-and-pinch is the primary and sufficient input**; the owner's PSVR2 Sense controllers are an optional enhancement via GameController and ARKit accessory anchors that duplicates on-panel controls and is never required. Two engineering rules follow: hover effects are system-rendered on gaze and the app learns the target only when the operator pinches, so touch targets stay large and nothing depends on app-side hover logic; and the live surface must be operable with one pinch per action, which rules out drag-heavy desktop idioms.

The platform's hard limits fall on the side of the design that was not chosen. Background execution is the iOS set: Apple's table lists `audio`, `voip`, `bluetooth-central`, `screen-capture`, `fetch`, `remote-notification` and `processing` for visionOS, with nothing that wakes an app on network traffic ([Configuring background execution modes](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes)), and an Apple engineer confirms that "visionOS, like all Apple platforms other than macOS, puts strict limits on what your app can do in the background" ([Apple Forums 751495](https://developer.apple.com/forums/thread/751495)). A remote client tolerates this: if the operator leaves the app or removes the headset, the websocket drops and NDI receive pauses while the show on the Mac continues, and the client reconnects on return. The M5 Vision Pro has 16 GB of unified memory, **Wi-Fi 6 (802.11ax)**, Bluetooth 5.3, refresh rates of 90, 96, 100 and 120 Hz, "up to 2.5 hours of general use", an operating range of 0 to 30 °C, and hardware decode for HEVC, H.264 and AV1 ([Apple Support 125436](https://support.apple.com/en-us/125436)); Wi-Fi 6 without 6E or 7 is the ceiling the NDI bandwidth plan is built around. NDI discovery uses Bonjour, and NDI's platform notes require the Info.plist "Bonjour Services" entry to list `_ndi._tcp.` "in order for NDI discovery to operate correctly", which on the iOS family also triggers the local-network privacy prompt the operator accepts once ([NDI Platform Considerations](https://docs.ndi.video/all/developing-with-ndi/sdk/platform-considerations)).

Debugging needs hardware, but less than a first guess suggests. The visionOS 26 Simulator handles CompositorServices progressive immersion and hover effects, both fixed in that release ([visionOS 26 Release Notes](https://developer.apple.com/documentation/visionos-release-notes/visionos-26-release-notes)), but it drives gaze and pinch with a mouse, so hand-tracking feel, Sense controllers, Wi-Fi behaviour and thermal behaviour need the device. The second-generation Developer Strap is press-reported at $299 with a USB-C port of up to 20 Gb/s, compatible with M2 and M5 headsets; Apple's page is behind a sign-in ([UploadVR](https://www.uploadvr.com/apple-developer-strap-upgrade/)). visionOS 27.0 shipped on 14 September 2026 ([MacRumors](https://www.macrumors.com/2026/09/14/apple-releases-visionos-27/)). Because the client is a SwiftUI package, the project decision is also to build it for macOS, keeping the daily loop on a Mac against a local OBS.

Distribution is simple because the client contains no GPL code. OBS is GPLv2 "or any later version" ([COPYING](https://github.com/obsproject/obs-studio/blob/master/COPYING)), but obs-websocket is a wire protocol and the NDI SDK is a vendor library under NDI's terms, which separate "commercial use" integrations from "personal and non-commercial use" ([NDI SDK](https://ndi.video/for-developers/ndi-sdk/)), so App Store, TestFlight and enterprise distribution are all open, gated only by review and NDI's licence tier. The visionOS enterprise APIs, "eligible for business use only", matter only if on-headset capture is ever wanted ([Apple enterprise APIs](https://developer.apple.com/documentation/visionos/building-spatial-experiences-for-business-apps-with-enterprise-apis)).

## The Mac host already exports the control bus and the video; only the property schema is missing

The OBS release facts bound the host side. The latest stable is **32.2.2 (14 August 2026)**, and "The macOS release of OBS Studio supports macOS 13.0 and newer" ([obsproject.com/download](https://obsproject.com/download)); 33.0.0 is at **RC3 (20 October 2026)** with no stable tag ([GitHub releases](https://github.com/obsproject/obs-studio/releases)). OBS 32.0 (22 September 2025) added the experimental Metal renderer for Apple Silicon ([OBS 32.0 release notes](https://obsproject.com/blog/obs-studio-32-0-release-notes)); OBS's blog says the backend "is explicitly marked as 'Experimental' in the application because it has some known quirks", chiefly around preview presentation ([How OBS Adopted Metal](https://obsproject.com/blog/obs-studio-gets-a-new-renderer)), and the default renderer on Apple Silicon remains OpenGL in 33.0-rc3 ([OBSApp.cpp](https://github.com/obsproject/obs-studio/blob/master/frontend/OBSApp.cpp)). OBS 32.1.0 (11 March 2026) added "partial support for Canvases to obs-websocket" ([32.1.0](https://github.com/obsproject/obs-studio/releases/tag/32.1.0)); OBS 33 stops starting the websocket server in Safe Mode, where third-party plugins are not loaded at all ([33.0.0-rc3 notes](https://newreleases.io/project/github/obsproject/obs-studio/release/33.0.0-rc3)), a state the headset must name when it finds nothing to talk to.

The control bus is already there. obs-websocket has shipped inside OBS since 28.0 and listens on port 4455 ([OBS KB: Remote Control Guide](https://obsproject.com/kb/remote-control-guide)). The protocol authenticates with a salted SHA-256 challenge, supports JSON or MsgPack, frame-synced request batches (`SerialFrame`), and bitmask event subscriptions in which the high-volume `InputVolumeMeters` event (every 50 ms) is opt-in ([protocol.md](https://raw.githubusercontent.com/obsproject/obs-websocket/master/docs/generated/protocol.md)). What it does not carry is the thing a generated settings UI needs most: it exposes an input's settings, default settings and the item lists of list-type properties (`GetInputSettings`, `GetInputDefaultSettings`, `GetInputPropertiesListPropertyItems`), but **not the full `obs_properties` schema**, the property types, ranges, steps, visibility and group structure that OBS's own dialogs are generated from. Its hotkey requests come "as-is", with the warning that "In 9/10 usages of hotkey requests, there exists a better, more reliable method via other requests", and it has no request for encoder settings, hotkey bindings or advanced audio configuration ([protocol.md](https://raw.githubusercontent.com/obsproject/obs-websocket/master/docs/generated/protocol.md)). That schema gap is exactly what the companion plugin fills.

The video path is already there too. DistroAV (formerly OBS-NDI) provides an NDI Source, an NDI Output and an "NDI Filter/Dedicated Output" per source, and requires "OBS v31.1.1 or higher" and "NDI Runtime v6.3 or higher" ([DistroAV README](https://raw.githubusercontent.com/DistroAV/DistroAV/master/README.md)). Its two program-level outputs are first-class OBS outputs named `NDI Main Output` and `NDI Preview Output`, both of kind `ndi_output`; "Both outputs are always created when OBS starts, including when they are disabled", "The Preview Output never carries audio", and each is controllable over obs-websocket's generic `GetOutputSettings`, `SetOutputSettings`, `StartOutput` and `StopOutput` ([DistroAV wiki: controlling outputs with obs-websocket](https://github.com/DistroAV/DistroAV/wiki/Controlling-DistroAV-outputs-with-obs‐websockets); [wiki Home](https://github.com/DistroAV/DistroAV/wiki)). DistroAV publishes no latency figures, only guidance: enable OBS's "Low latency Audio Buffering Mode" because otherwise NDI's "latency buffer increasing overtime ... causes audio and video sync issues" ([DistroAV wiki: Extras](https://github.com/DistroAV/DistroAV/wiki/4.-Extras)). Its latest release is 6.2.2 (13 October 2026), and it registers no obs-websocket vendor, so the companion plugin drives its outputs through the generic output requests ([main-output.cpp](https://github.com/DistroAV/DistroAV/blob/master/src/main-output.cpp)). The host requirement is therefore stock OBS 31.1.1 or newer with bundled obs-websocket, DistroAV and NDI Runtime 6.3 or newer, and **no custom video plugin**.

On the headset, the NDI SDK release notes record "Added visionOS support to Apple SDKs" in NDI 6.2 (June 2025) and "Added missing NDI receiver advertiser API symbols to the visionOS library" in 6.3.2 (April 2026) ([NDI SDK Release Notes](https://docs.ndi.video/all/developing-with-ndi/sdk/release-notes)); the platform page documents iOS finding, sending and receiving ([Platform Considerations](https://docs.ndi.video/all/developing-with-ndi/sdk/platform-considerations)), and ARM builds "require NEON support" ([CPU Requirements](https://docs.ndi.video/all/developing-with-ndi/sdk/cpu-requirements)). NDI's marketing page still omits visionOS ([NDI SDK](https://ndi.video/for-developers/ndi-sdk/)), which is why the first Phase 0 task is to link and receive with 6.3.2 under the visionOS 26 and 27 SDKs. The structural benefit of NDI over a bespoke feed is that any NDI source on the network, cameras and other machines included, becomes a tile in the headset's multiview.

The in-process surfaces matter for the companion plugin and the later Mac mode. `obs-frontend-api` is a shared library of roughly **93 documented functions** (105 prototypes in the header) covering scenes, transitions, studio mode, outputs, profiles, scene collections, docks and `obs_frontend_reset_video` ([reference-frontend-api](https://docs.obsproject.com/reference-frontend-api); [obs-frontend-api.h](https://github.com/obsproject/obs-studio/blob/master/frontend/api/obs-frontend-api.h)). The Frontends page states the two libobs facts that shape settings apply: video "can be reconfigured by calling obs_reset_video() as long as no outputs are active", while audio "is not able to be reset once initialized; libobs must be fully shutdown in order to reconfigure audio settings" ([docs.obsproject.com/frontends](https://docs.obsproject.com/frontends)). The Canvas API "should be considered unstable", and "If you are developing a plugin that utilizes canvases, proceed with great caution" ([reference-canvases](https://docs.obsproject.com/reference-canvases)). `obs_get_main_texture()`, `obs_render_main_texture_src_color_only()` and `obs_add_raw_video_callback2()` are exported from `libobs/obs.h` with **no entry in the public reference** ([obs.h](https://github.com/obsproject/obs-studio/blob/master/libobs/obs.h)); they matter only for the Mac immersive mode. Finally, the OBS 33 loader overhaul moves first-party plugins into a `core` folder and changes third-party locations on other platforms, but "Plugin locations on macOS have not been changed" ([OBS KB: Legacy plugin locations](https://obsproject.com/kb/legacy-plugin-locations); [PR #13594](https://github.com/obsproject/obs-studio/pull/13594)), so on the Mac host the companion plugin is an ordinary bundle and the fork's upstream diff is one plugin directory.

## Recommended architecture: native SwiftUI app, obs-websocket control, NDI video, one companion plugin

The architecture that survives the constraints and reflects the owner's decisions has three loosely coupled pieces. First, **OBS on the Mac stays stock plus two plugins**: upstream `frontend/` and libobs untouched, obs-websocket enabled, DistroAV installed with NDI Runtime 6.3+, and this fork's companion plugin registering vendor requests. Second, the **Vision Pro client is a native SwiftUI/RealityKit app containing no libobs**: an obs-websocket control layer, a vendor-request layer for schemas, tally and pairing, a generated-form engine for every settings surface, hand-built spatial panels for the live surface (Program and Preview wall, multiview, mixer, scene and source lists, transitions, outputs), and an NDI receiver. It lives in the Shared Space, offers an optional immersive stage, and is built for macOS from the same SwiftUI package for desk-side debugging against a local OBS. Third, a small **pointer-and-action abstraction** with gaze plus pinch as the primary backend and an optional PSVR2 Sense backend that only duplicates what the panels already offer. The websocket-plus-NDI design does not preclude other OBS hosts, but this plan targets a Mac.

Bandwidth and latency are the risks to plan around, because the headset is Wi-Fi 6 only ([Apple Support 125436](https://support.apple.com/en-us/125436)). Full-bandwidth 1080p60 NDI is on the order of 125 Mbps per stream and the SDK offers a lowest-bandwidth "proxy" receive mode around 640 px wide; both figures are NDI's general guidance rather than measurements from this research, which is why Phase 0 checks them. The plan is therefore **proxy-bandwidth receive mode for every multiview tile and full bandwidth only for the selected monitor**, a dedicated 5 GHz access point for the headset, and congested Wi-Fi named as a known failure mode that must degrade visibly (tiles drop frame rate or freeze with a stale indicator) before the Program monitor is touched, rather than fail silently. No primary source gives an NDI-to-headset latency: DistroAV publishes no figures, and the OBS forum carries both a 120 to 140 ms report and drift reports against DistroAV, about 250 ms growing to seconds in one sync mode and 40 ms per 10 minutes in another ([OBS forum](https://obsproject.com/forum/threads/distroav-network-audio-video-in-obs-studio-using-ndi%C2%AE-technology.69240/page-24)). The app therefore measures and displays its own feed latency and bitrate per source and reconnects to obs-websocket, each NDI source and the vendor channel independently; Phase 0 includes a timecode-based glass-to-glass measurement on a clean AP and on congested Wi-Fi.

**WebRTC/WHIP is documented only as a future WAN alternative.** OBS's built-in `whip_output` measured "~120 Milliseconds from Broadcaster to Playback" in its original PR ([PR #7926](https://github.com/obsproject/obs-studio/pull/7926)), OBS 31.0 "Restored STUN support for WHIP output" ([31.0.0](https://github.com/obsproject/obs-studio/releases/tag/31.0.0)), and VDO.Ninja notes that stock OBS "lacks the ability to perform NAT traversal" beyond that ([VDO.Ninja](https://docs.vdo.ninja/guides/obs-whip-output-settings)). On the headset, LiveKit's Swift SDK officially "supports macOS, tvOS, and visionOS" ([LiveKit](https://docs.livekit.io/transport/sdk-platforms/swift.md)), while the popular stasel WebRTC xcframework fails to build for visionOS ([Swift Package Index](https://swiftpackageindex.com/builds/C952AB2E-BCF6-4781-89C7-92CD36926F26)). It works off-LAN at a fraction of NDI's bitrate, which is the case for building it later; its cost is a second video stack and a signaling service the LAN product does not need.

The **companion plugin** is the piece that turns a remote into a parity client, and its mechanism is read from source rather than inferred. `lib/obs-websocket-api.h` declares `OBS_WEBSOCKET_API_VERSION 3`; a plugin calls `obs_websocket_register_vendor()` and `obs_websocket_vendor_register_request()` "ALWAYS ... ONLY VIA `obs_module_post_load()`", each request callback receives an `obs_data_t` request and fills an `obs_data_t` response, events leave through `obs_websocket_vendor_emit_event()`, and the header back-fills API version 1 when obs-websocket is absent ([obs-websocket-api.h](https://raw.githubusercontent.com/obsproject/obs-websocket/master/lib/obs-websocket-api.h)). Server-side, incoming messages are dispatched on obs-websocket's thread pool and `PerformVendorRequest` invokes the callback **synchronously** under shared locks, so vendor callbacks run off the UI and graphics threads and the plugin must marshal any libobs or frontend work onto the right thread itself ([WebSocketServer.cpp](https://github.com/obsproject/obs-websocket/blob/master/src/websocketserver/WebSocketServer.cpp); [WebSocketApi.cpp](https://github.com/obsproject/obs-websocket/blob/master/src/WebSocketApi.cpp)). On the wire, `CallVendorRequest {vendorName, requestType, requestData}` returns `{vendorName, requestType, responseData}`, `VendorEvent` carries `{vendorName, eventType, eventData}` under the `Vendors` subscription, vendor requests take part in ordinary request batches, there is **no streaming**, and **no payload size limit is stated** anywhere in the protocol document ([protocol.md CallVendorRequest](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md#callvendorrequest)). No core request enumerates registered vendors, so the plugin follows the convention of a handshake request for discovery, as Advanced Scene Switcher does with `AdvancedSceneSwitcherVersion` and Aitum Vertical Canvas with `version` ([websocket-api.cpp](https://github.com/WarmUpTill/SceneSwitcher/blob/master/lib/utils/websocket-api.cpp); [vertical-canvas.cpp](https://github.com/Aitum/obs-vertical-canvas/blob/master/vertical-canvas.cpp)). The mechanism is the sanctioned extension point in practice: the maintainers closed #273 "Allow 3rd-party OBS plugins to expose RPC methods" as "basically done" with it ([#273](https://github.com/obsproject/obs-websocket/issues/273)), and StreamUP (66 request names including deprecated aliases), Aitum Stream Suite (32) and Aitum Vertical Canvas (21) ship on it; StreamUP's requests cover scale filtering, show and hide transitions, blend method, mono downmix and open-properties dialogs, exactly the gaps still open upstream ([streamup.cpp](https://github.com/StreamUPTips/obs-streamup/blob/master/streamup.cpp); [obs-websocket.cpp](https://github.com/Aitum/obs-aitum-stream-suite/blob/main/src/utils/obs-websocket.cpp)).

The plugin itself is plain C against libobs and `obs-frontend-api`, with no UI toolkit dependency. It registers one vendor namespace that serves full `obs_properties` schemas for sources, filters, transitions, outputs and encoders so the headset can generate settings forms; emits tally and selection events; handles device pairing with a QR code carrying host, port and a pairing token, as ProducerPad does; and enables DistroAV's Main and Preview outputs and per-source NDI filters on request. It touches neither `frontend/` nor libobs and loads as an ordinary module, which is what keeps the fork rebaseable.

## Full control parity is reachable in four tiers, and the Settings dialog is the hard one

The owner's requirement is parity of capability with the desktop app, not parity of screens. The design that delivers it is a generated-form engine driven by property schemas for the long tail of dialogs, with hand-built spatial panels reserved for the live surface. The table sorts every desktop capability into the channel that provides it; request names are quoted only where the protocol document lists them.

| Tier | Channel | Covers | Notes |
|---|---|---|---|
| 1 | obs-websocket, native | Scenes and scene collections; sources and inputs; scene items and transforms (`SetSceneItemTransform`); filters (full CRUD, order, enabled, settings); transitions and their settings and duration (`SetCurrentSceneTransition`); studio mode and T-bar (`SetStudioModeEnabled`, `TriggerStudioModeTransition`, `SetTBarPosition`); stream, record, replay buffer and virtual camera (`StartStream`, `StartRecord`, `PauseRecord`, `SplitRecordFile`, `CreateRecordChapter`, `StartVirtualCam`); audio volume, mute, monitoring and sync offset, with `InputVolumeMeters` at 50 ms; hotkey triggering (`TriggerHotkeyByName`, documented "as-is"); projectors (`OpenVideoMixProjector`, `OpenSourceProjector`); screenshots (`GetSourceScreenshot`); profiles; video settings (`GetVideoSettings`), stream service settings, record directory and arbitrary profile parameters in the Config category; stats (`GetStats`); media input control (`TriggerMediaInputAction`); canvases (partial, since 32.1) and WebRTC simulcast | Everything on this row is in the protocol document ([protocol.md](https://raw.githubusercontent.com/obsproject/obs-websocket/master/docs/generated/protocol.md)); it is most of what an operator touches during a show |
| 2 | Companion plugin vendor requests over the same socket | Full `obs_properties` schemas for sources, filters, transitions, outputs and encoders; stream and record encoder settings, which live in per-profile JSON files the websocket never sees; hotkey binding configuration; audio device and advanced-audio configuration; multiview and projector configuration; anything reachable only through `obs-frontend-api` in-process | Plain C against libobs and `obs-frontend-api`; API v3, synchronous `obs_data_t` callbacks on the worker pool, no streaming ([obs-websocket-api.h](https://raw.githubusercontent.com/obsproject/obs-websocket/master/lib/obs-websocket-api.h)); the mechanism StreamUP, Aitum and Advanced Scene Switcher ship on |
| 3 | Settings dialog apply semantics | Output, video and audio settings applied the way the desktop applies them | Writing config is easy; applying it means mirroring the desktop frontend's apply order (video reset, audio reset, output rebuild) from its `settings/` module (9,659 lines in this checkout; [upstream tree](https://github.com/obsproject/obs-studio/tree/master/frontend/settings)), which is upstream-churn exposure. Scope output, video and audio first because they are show-critical; treat the remainder as config writes effective on next launch. This is the main upstream-sync risk in the plan |
| 4 | Desktop-app-level features | Plugin installation and the plugin manager, the auto-configuration wizard, scene collection importers, remux, update checks, log upload, theme editing, service chat docks and custom browser docks | All in scope by owner decision; sorted below into portable logic the companion plugin hosts, config writes that need a frontend hook to apply live, and filesystem-plus-restart operations |

Two libobs facts fix the shape of Tier 3. Because video "can be reconfigured by calling obs_reset_video() as long as no outputs are active" and audio cannot be reset without a full shutdown ([docs.obsproject.com/frontends](https://docs.obsproject.com/frontends)), the headset must surface the same "stop outputs first" and "restart required" states the desktop shows, and the companion plugin must drive the apply through `obs-frontend-api` (`obs_frontend_reset_video` and the output handlers) rather than write config and hope. Encoder settings are the other trap: the desktop reads and writes them as per-profile JSON that the websocket never sees, so the plugin exposes them with their encoder `obs_properties` schema and the generated form edits them like any source. The generated-form engine is the most reusable component in the project: one renderer over a schema, which the later Mac immersive mode reuses.

Tier 4 is in scope by the owner's decision that **there is no desktop-only tier**, and the useful distinction is what kind of work each feature needs. The first group is portable logic the companion plugin can host directly because it has no UI dependency: the scene collection importers are self-contained converter code under `frontend/importers` (`classic.cpp`, `sl.cpp`, `studio.cpp`, `xsplit.cpp`) ([upstream tree](https://github.com/obsproject/obs-studio/tree/master/frontend/importers)), remux is FFmpeg muxing behind `frontend/dialogs/OBSRemux.cpp` ([upstream](https://github.com/obsproject/obs-studio/blob/master/frontend/dialogs/OBSRemux.cpp)), log upload and update checks are plain HTTP flows, and the auto-configuration wizard's bandwidth and encoder tests live under `frontend/wizards` (`AutoConfig*.cpp`, `TestMode.hpp`) ([upstream tree](https://github.com/obsproject/obs-studio/tree/master/frontend/wizards)) and can be extracted or reimplemented against libobs alone and driven by vendor requests. The second group is config writes that need a frontend hook to apply live: theme selection and plugin enable/disable are config changes the desktop applies through private frontend code, and the public `obs-frontend-api` offers only `obs_frontend_is_theme_dark()` on the theme side ([obs-frontend-api.h](https://github.com/obsproject/obs-studio/blob/master/frontend/api/obs-frontend-api.h)), so from the headset they take effect on next launch unless small frontend-API additions land upstream (a set-theme or reload-theme call, a reload-docks call), which ties them to the upstreaming track. The third group is filesystem and restart operations: plugin installation is unpacking into the macOS plugin folder, which OBS 33 did not move ([OBS KB: Legacy plugin locations](https://obsproject.com/kb/legacy-plugin-locations)), plus an OBS restart the headset can request through the plugin.

Chat docks stay in scope and must obey the desktop configuration. In this checkout, custom browser docks are persisted in the user config as JSON under `BasicWindow/ExtraBrowserDocks` (title plus URL), read and written in `frontend/widgets/OBSBasic_Browser.cpp` and `frontend/docks/YouTubeAppDock.cpp` ([OBSBasic_Browser.cpp](https://github.com/obsproject/obs-studio/blob/master/frontend/widgets/OBSBasic_Browser.cpp); [YouTubeAppDock.cpp](https://github.com/obsproject/obs-studio/blob/master/frontend/docks/YouTubeAppDock.cpp)); the Twitch, YouTube and Restream chat, info and feed docks are built in `frontend/oauth/TwitchAuth.cpp`, `YoutubeAuth.cpp` and `RestreamAuth.cpp` from the authenticated account's URL and opened through `cef->create_widget(..., panel_cookies)`, where `panel_cookies` is a per-profile CEF cookie manager created under `obs_profile_cookies/<Panels/CookieId>` ([TwitchAuth.cpp](https://github.com/obsproject/obs-studio/blob/master/frontend/oauth/TwitchAuth.cpp); [OBSBasic_Browser.cpp](https://github.com/obsproject/obs-studio/blob/master/frontend/widgets/OBSBasic_Browser.cpp)). The consequence is clean on the data side and awkward on the session side: the companion plugin can publish the desktop's dock list, titles, URLs, visibility and layout to the headset, which renders each in a `WKWebView` following the desktop configuration, and edits on either side write the same config; but **the CEF cookie store cannot be shared with a visionOS web view**, so the operator signs into Twitch, YouTube or Restream once inside the headset, and any dock that depends on the desktop's OAuth session rather than a public URL needs the plugin to hand over a URL the headset can open on its own.

## The Mac immersive studio is a later optional mode, and Mac Virtual Display is never a dependency

Apple's only sanctioned path from a Mac to the headset's compositor is `RemoteImmersiveSpace`, a SwiftUI scene available on macOS 26.0 and no other platform, "a container for compositor content that your macOS app presents on a user's chosen visionOS device"; the remote device "hides all other visible apps" while it is open, and "The system allows only one immersive space to be open at a time" ([RemoteImmersiveSpace](https://developer.apple.com/documentation/swiftui/remoteimmersivespace)). WWDC25 session 294 states that "On Mac, only the progressive and full immersion styles are supported", that the Mac hosts the CompositorLayer and ARKit session, that "any input device connected to your Mac" works including gamepads, and that the motivation is rendering "without being constrained by the power usage of Vision Pro" ([WWDC25 294](https://developer.apple.com/videos/play/wwdc2025/294/)); a Vision Pro engineer adds that RealityKit is unavailable there, so rendering is Metal 3 or Metal 4 ([Apple Forums 787528](https://developer.apple.com/forums/thread/787528)). The visionOS 26 release notes show that a session can run over a "wired USB connection" as well as Wi-Fi, that Apple-silicon Macs could show "video stalls, blurry content, and black rendering on the sides" with the `renderQuality` API as the lever, and that "If you port an app using Xcode template or Metal 4 with ProgressiveImmersionStyle for macOS spatial rendering, the app will crash on macOS", with Full as the workaround ([visionOS 26 Release Notes](https://developer.apple.com/documentation/visionos-release-notes/visionos-26-release-notes)); visionOS 27 fixed device discovery ([visionOS 27 Release Notes](https://developer.apple.com/documentation/visionos-release-notes/visionos-27-release-notes)). **Apple publishes no latency, resolution, refresh or bitrate figure for RemoteImmersiveSpace**; Spatial Render's "2.5K@90Hz per eye" is a vendor claim and the only number in the public record.

Read against the product, this mode wins on monitoring fidelity (zero-copy, uncompressed Program on the same GPU as libobs, no NDI encode at all) and on keeping everything on the Mac; it loses on UI toolkit (Metal only, every control hand-rendered into the `CompositorLayer`), on immersion (full or progressive only, hiding every other app, so nothing can sit on the real desk), and on maturity (first release in macOS 26, progressive crashed in Apple's template, no published latency). That is why it is a later optional "immersive studio" mode rather than the product, and why it starts with a bounded spike: composite a SwiftUI-rendered texture into the `CompositorLayer` at text quality an operator can read, and establish whether Sense controller input and hover effects are forwarded to the Mac in that mode, which Apple's pages do not say. If both hold, the Mac app renders the studio from libobs's Metal texture through the exported but undocumented `obs_get_main_texture()` path ([obs.h](https://github.com/obsproject/obs-studio/blob/master/libobs/obs.h)) and reuses the Phase 1 control, vendor and form layers in Swift. If the spike fails, the native remote already covers every operator task.

Mac Virtual Display is retained here only to state that the product must not depend on it. It shows only the Mac's main display, connects to one Mac at a time, needs macOS 14 or later, and reaches Standard 5120 by 2880 on Apple silicon, Wide 6720 by 2880 and Ultrawide **10240 by 2880 pixels**, the latter two requiring Apple silicon, macOS 15.2 and visionOS 2.2 ([Apple Support 118521](https://support.apple.com/118521)), at up to 120 Hz on the M5 model ([Apple Newsroom](https://www.apple.com/newsroom/2025/10/apple-vision-pro-upgraded-with-the-m5-chip-and-dual-knit-band/)). It is flat, undocumented for latency, and a visionOS 26 bug-fix note is the only evidence it has ever run alongside a `RemoteImmersiveSpace` ([visionOS 26 Release Notes](https://developer.apple.com/documentation/visionos-release-notes/visionos-26-release-notes)). An operator may use it, but every capability in this plan must be reachable in the headset app itself, which is what makes the parity tiers load-bearing.

## Upstreaming runs on a dual track, and nothing in the plan waits for a merge

The upstream evidence argues for patience and narrow scope. The obs-websocket tracker holds **86 open feature requests and 23 open PRs**, and every one of the headset client's gaps already has an open issue, most with zero maintainer comments: the property-schema request #1099 (February 2023) and #1227, advanced output settings #575 (2020), encoder selection #1288, audio monitoring devices #798 (where tt2468 proposed request names in 2021 and nothing followed), projector control #949 and #1301, scene collection import #1240, and scene-item show/hide transitions #906, where tt2468 wrote in 2022 that it "is planned to be implemented ... in a future version" and pings through 2025 went unanswered ([#1099](https://github.com/obsproject/obs-websocket/issues/1099); [#906](https://github.com/obsproject/obs-websocket/issues/906); [#798](https://github.com/obsproject/obs-websocket/issues/798); [open feature requests](https://github.com/obsproject/obs-websocket/issues?q=is%3Aissue+is%3Aopen+label%3A%22Issue%3A+Feature+Request%22+sort%3Acreated-desc)). PRs implementing three of those gaps sit unreviewed: #1322 scene-item show/hide transitions (November 2025), #1350 audio mono and #1352 blend method (both August 2026) ([PR #1322](https://github.com/obsproject/obs-websocket/pull/1322); [open PRs](https://github.com/obsproject/obs-websocket/pulls?q=is%3Apr+is%3Aopen+sort%3Acreated-asc)). No written scope policy exists; the maintainer statements on record are tt2468's "out of the scope" ruling on video ([#545](https://github.com/obsproject/obs-websocket/issues/545)), PatTheMav's "a remote control client (what websockets is made for) should not futz around with canvases" and Warchamp7's "the use of name is going to be removed entirely in favor of UUIDs" on the canvas PR ([#1314](https://github.com/obsproject/obs-websocket/pull/1314)), and tt2468's "We need to do an RPC version bump in order to expose events from non-main canvases", which acknowledges rpcVersion 2 as the vehicle for breaking changes with no date ([#1331](https://github.com/obsproject/obs-websocket/pull/1331)).

Capacity is the bottleneck. Commits fell from 550 in 2021 to 22 in 2025 and 48 in 2026 to date; since 2024 essentially every commit is committed by tt2468 or RytoEX, and RytoEX wrote on a waiting PR "I am not familiar enough with websockets or this PR to provide a review" ([commits](https://github.com/obsproject/obs-websocket/commits/master); [#1229](https://github.com/obsproject/obs-websocket/pull/1229)). Time to merge splits by shape: narrow parity requests on existing libobs objects from known contributors landed in **6 to 37 days** (#1265, #1224, #1187), larger or conceptually new changes took **178 days** (#1314 canvases) to about 10.5 months (#1108), outsider request PRs wait 28 to 49 months with no maintainer comment, and no request-adding PR from a non-core author has merged since June 2024 ([#1187](https://github.com/obsproject/obs-websocket/pull/1187); [#1224](https://github.com/obsproject/obs-websocket/pull/1224); [#1265](https://github.com/obsproject/obs-websocket/pull/1265); [#1314](https://github.com/obsproject/obs-websocket/pull/1314); [#1189](https://github.com/obsproject/obs-websocket/pull/1189)). Websocket discussion belongs in the main OBS Discord's #plugins-and-tools channel ([ideas #3298](https://ideas.obsproject.com/posts/3298/add-a-websocket-channel-under-development-on-the-main-obs-server)).

The recommendation is therefore dual-track. **Ship everything as vendor requests first**, which is what StreamUP and Aitum do for the same gaps. Then upstream a short list of narrow, UUID-first, non-breaking parity requests, each with the documentation comments that CI regenerates `protocol.md` from and a test script, timed before an OBS release's feature freeze: an `obs_properties` schema request closing #1099 and #1227 (novel, but it needs no OBS core change because libobs already exposes property enumeration), per-scene-item show and hide transitions closing #906 by supporting the drafted #1322, and blend method and mono downmix by supporting #1352 and #1350 ([Contributing Guidelines](https://github.com/obsproject/obs-websocket/wiki/Contributing-Guidelines); [docs/README.md](https://github.com/obsproject/obs-websocket/blob/master/docs/README.md)). Anything touching projectors, docks or multiview starts as an `obs-frontend-api` PR in obsproject/obs-studio, not as an obs-websocket PR: those items carry the "Requires OBS Changes" label on the websocket tracker, and the missing primitives are the ones the ideas board already requests, `obs_frontend_close_projector` (#2185) and `obs_frontend_list_docks` (#2752) ([Requires OBS Changes](https://github.com/obsproject/obs-websocket/issues?q=label%3A%22Requires+OBS+Changes%22+sort%3Aupdated-desc); [ideas #2185](https://ideas.obsproject.com/posts/2185/add-obs_frontend_close_projector-to-the-obs-frontend-api); [ideas #2752](https://ideas.obsproject.com/posts/2752/add-obs_frontend_list_docks-to-the-obs-frontend-api)). The reload-theme and reload-docks hooks from Tier 4 belong on that same obs-studio track. Program and Preview screenshots (#1130, #1189, #1257) stay on the vendor side, since the headset does not need them once NDI carries both feeds. Each accepted upstream request retires a vendor request in the plugin, and **nothing in the phased plan depends on an upstream merge**.

## Phased plan: measure NDI first, ship the native app, then the plugin, then the immersive studio

| Phase | Goal | Deliverables | Exit criterion |
|---|---|---|---|
| 0: Decisions and spikes | Remove the unknowns that gate Phase 1 | NDI proxy-mode and full-bandwidth test on a Vision Pro over Wi-Fi 6 with a timecode glass-to-glass measurement, on a dedicated 5 GHz AP and again on congested Wi-Fi; NDI 6.3.2 link-and-receive check under the visionOS 26 and 27 SDKs; vendor-request spike (register a `version` handshake request and one event, push a full encoder schema through `CallVendorRequest` on 5.7.4 and 5.7.6 to find practical payload limits and null/array edge cases); app licence choice and NDI licence tier; App Store versus TestFlight versus enterprise for the pilot | Program at full bandwidth plus four proxy tiles stable on a dedicated 5 GHz AP with a measured latency number; a schema-sized vendor request round-trips |

| 3: Mac immersive studio | Full-fidelity spatial monitoring without a headset binary | Spike: SwiftUI-rendered texture composited into `CompositorLayer` with readable text, Sense and hover forwarding checked on macOS 26 plus visionOS 26 hardware; then, if it passes, a Swift `RemoteImmersiveSpace` host with libobs on Metal sharing the device, reusing the control, vendor and form layers | Mac-hosted immersive show with measured latency, or a documented decision to keep the mode shelved |

| Later, optional | Widen reach | WebRTC/WHIP WAN path for off-LAN operation via LiveKit's visionOS-capable SDK; an enterprise "capture" SKU only if on-headset capture (visionOS 27 ScreenCaptureKit or enterprise entitlements) ever becomes relevant to the Vision Pro product ([ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit)) | Demand-driven |

Parallel development works because the layers separate cleanly. The control, vendor-request and generated-form layers are debugged on a Mac against stock OBS; the SwiftUI client runs on macOS and in the visionOS Simulator for layout and against a real OBS for data; and the headset is needed early only for gaze-and-pinch feel, Sense tracking, Wi-Fi behaviour and thermal behaviour. Plugin work can start as soon as the Phase 0 vendor-request spike passes, because the schema request is what unblocks the generated-form engine.

## Conclusion

The research reframes the project from "an immersive port of OBS" into "the first non-desktop OBS control surface", and once that frame is adopted the headset becomes incidental to most of the hard work. obs-websocket already carries nearly every live control, DistroAV already publishes Program and Preview as NDI outputs that the same websocket can switch on, and NDI's SDK already runs on visionOS, so the client needs no video code of its own and the host needs no fork of libobs or the desktop frontend. What OBS does not export is the schema its own dialogs are generated from, and that gap, closed by a vendor-request plugin in plain C, is what separates a scene switcher from a client with full control parity; the desktop-app-level features that remain are portable logic the same plugin can host, config writes awaiting two small upstream hooks, or a plugin folder and a restart.

Two implications follow. The risks are concentrated rather than spread: Wi-Fi 6 bandwidth for NDI is measured in Phase 0 before anything is built on it, and the Settings dialog's apply semantics is scoped to the show-critical pages and reviewed on every OBS minor. And the upstream record says to treat obs-websocket as a stable wire format rather than a venue for feature work: vendor requests ship on the project's own schedule, narrow parity PRs are offered when a maintainer is likely to engage, and the Mac `RemoteImmersiveSpace` studio is promoted from "later" to "next" only if a short spike shows that hand-rendered UI is legible and controller input reaches the Mac. If that spike fails, the native remote already covers every operator task, and the Mac path stays a fidelity upgrade rather than a dependency.
