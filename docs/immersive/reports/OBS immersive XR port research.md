# Immersive OBS: Build a Remote, Not a Port

Nobody has shipped OBS Studio inside a headset, and the research plus the owner's strategy decisions since the first draft converge on one design: the Vision Pro product is a **native SwiftUI/RealityKit visionOS app that contains no libobs and no Qt**, controls a desktop OBS over obs-websocket, receives Program, Preview and any other network feed as **NDI** through the outputs DistroAV already provides, and must stand alone for everything an operator needs during a show, with **full control parity** with the desktop app as the goal and no dependence on Mac Virtual Display anywhere. libobs stays on the Mac or PC where its capture, encoders and the stock Qt Widgets UI already work; the only code added to this fork is a small companion plugin, plain C against libobs, that extends obs-websocket with vendor requests for property schemas, tally, pairing and DistroAV output control. The prior art is thin: a nine-commit SteamVR overlay that controls OBS without video, four iPad obs-websocket remotes that run on Vision Pro in iPad-compatibility mode, and desktop-mirroring overlays. Qt Quick 3D XR, the obvious single-codebase route, was re-checked against the rendered Qt 6.12.0 documentation and the live bug tracker: every XR type is stamped "technology preview", visionOS needs a static from-source Qt build, apps are immersive-only with no windowed-to-immersive transition, passthrough is an unresolved launch-time Info.plist setting (QTBUG-129736), and two P1 visionOS regressions were fixed only in 6.12.0/6.12.1, so Qt is deferred to the Steam Frame PCVR client decision alongside Godot and raw OpenXR. Qt Widgets cannot be hosted in Qt Quick 3D at all, so any Qt headset UI would be a new QML shell, never a port of the **88,669-line Widgets frontend** in this checkout. Apple's `RemoteImmersiveSpace` Mac path wins on monitoring fidelity but is Metal-only, full or progressive immersion only, hides every other app and first shipped in macOS 26, so it becomes a later optional "immersive studio" mode. Input is gaze-and-pinch first, PSVR2 Sense controllers as an optional enhancement, and tracked controllers on Steam Frame, which per Valve's own pages has no hand tracking. Parity means everything the desktop app can do, with no desktop-only tier: plugin installation, the auto-config wizard, importers, remux, theme and chat docks are all reachable from the headset, sorted by whether the companion plugin can host the logic, whether a config write needs an upstream frontend hook to apply live, or whether it is a filesystem-plus-restart operation. The hardest parity item is not any panel but the Settings dialog's apply semantics, which is where upstream-sync risk concentrates, and an upstreaming track exists to retire vendor requests as obs-websocket and `obs-frontend-api` accept them.

A note on sourcing: a verification pass reached doc.qt.io, bugreports.qt.io, docs.obsproject.com, obsproject.com, apps.apple.com, developer.apple.com, support.apple.com, Valve's store and Steamworks pages, Gamers Nexus and ndi.video, so the facts below cite rendered primary pages or Qt's and OBS's git sources. What remains unverified from a primary source is listed in the open-questions section; the main items are Valve's price text and the "Windows-only wireless adapter" support article, Apple's Developer Strap page (sign-in only), any Apple or NDI latency figure for the transports discussed, Apple's own position on GPL apps in the App Store, and LiveKit's official visionOS limitations page; the obs-websocket vendor-request API was read from its header and server source in a later pass and is now cited directly. Strategy decisions made by the project owner and the coordinating engineer after the first draft are marked as project decisions, not research findings.

## Nobody has put OBS in a headset; the nearest prior art is a nine-commit overlay and four iPad remotes

The OBS forum's own search returns **"No results found."** for "Vision Pro", "visionOS", "QML" and "SteamVR overlay", and the project's GitHub Discussions return "There are no matching discussions" for "vision pro" ([OBS forum search](https://obsproject.com/forum/search/search?keywords=%22Vision+Pro%22); [Discussions](https://github.com/obsproject/obs-studio/discussions?discussions_q=vision+pro)). The OBS resource manager lists exactly two VR plugins, both Windows-only capture sources that bring the headset view into OBS: OpenVR-Capture (v1.8.4, minimum OBS 30.0.0, last updated 4 May 2025) and the original OpenVR input plugin (minimum OBS 19.0.0, last updated 27 February 2026) ([OpenVR-Capture](https://obsproject.com/forum/resources/openvr-capture.2038/); [OpenVR input plugin](https://obsproject.com/forum/resources/openvr-input-plugin.534/)); elliotttate's OpenXR-Layer-OBSMirror (MIT, 54 stars) is the same direction as an OpenXR API layer ([GitHub](https://github.com/elliotttate/OpenXR-Layer-OBSMirror)). These matter only to avoid confusing them with the problem at hand.

The one purpose-built "control OBS from inside VR" codebase is nicolas-riera's **OBS-SteamVR-Overlay**: a C++ SteamVR overlay with no desktop window that attaches to a controller or wrist, adds a dashboard tab, speaks obs-websocket v5, and covers recording, streaming, virtual camera, replay buffer, scene selection, studio mode and transitions, a full audio mixer with VU meters and per-track routing, performance stats and a layout editor; it has **no preview or program video**, an unstated licence, 1 star and 9 commits ([GitHub](https://github.com/nicolas-riera/OBS-SteamVR-Overlay)). Its feature list is the best available scoping document for the live surface of an in-headset controller, and its ergonomics (wrist panel revealed by turning the wrist toward the eyes, laser or trigger cursor, hide when disconnected) are a sensible starting point. What streamers actually use is the "flat window in 3D" pattern: Desktop+ (GPL-3.0, roughly 585 stars) mirrors desktop windows into OpenVR overlays ([GitHub](https://github.com/elvissteinjr/DesktopPlus)), WayVR (GPL-3.0, roughly 1.5k stars) does the same over OpenXR and advertises "experimental headless support on Steam Frame" ([GitHub](https://github.com/galister/wlx-overlay-s)), and OVR Toolkit sells wrist macros pitched for "changing OBS scenes" ([Steam](https://store.steampowered.com/app/1068820/OVR_Toolkit__Desktop_Overlay/)).

On the Apple side, direct reads of the US App Store correct the first draft: **four of the five** OBS remotes checked list "Apple Vision" compatibility, all as "Designed for iPad" apps and none as a native visionOS build. OBS Controller ($1.99, visionOS 1.0 or later, v0.11.0 of 13 January 2026) is "a simple mobile scene switcher" with no video ([App Store](https://apps.apple.com/us/app/obs-controller/id1547228500)). OBS Blade (free, GPL-3.0 Flutter, visionOS 1.0 or later, v4.2.0 of 21 October 2026) advertises a "live scene preview" ([App Store](https://apps.apple.com/us/app/obs-blade/id1523915884)). **ProducerPad** (iOS 18, visionOS 2.0 or later) is the closest template to the chosen design: "Monitor Program and Preview with ProducerPad Feed or NDI", where "NDI monitoring requires a compatible NDI setup" ([App Store](https://apps.apple.com/us/app/producerpad/id6755590424)). CTD Live Mobile ($1.99, visionOS 26.0 or later) confirms the screenshot-polling mechanism everyone infers: "The app now asks OBS for the size each pane will really be drawn at", with a TAKE button for preview-to-program ([App Store](https://apps.apple.com/us/app/ctd-live-mobile/id6780304134)). Touch Portal lists no Apple Vision line ([App Store](https://apps.apple.com/us/app/touch-portal/id1410172542)). None is more than a scene switcher with thumbnails; the parity goal set by the owner is a different product category.

That control-versus-video split is forced by the protocol. OBS 32.2.2 bundles obs-websocket **5.7.4** and OBS 33.0-rc3 (and this tree) bundle **5.7.6**, both rpcVersion 1 ([CMakeLists](https://raw.githubusercontent.com/obsproject/obs-websocket/master/CMakeLists.txt)); the only image facility is `GetSourceScreenshot`, a base64 image per call sized 8 to 4096 px, and a grep of the protocol document for "video stream", "frame stream" or "continuous" returns nothing ([protocol.md](https://raw.githubusercontent.com/obsproject/obs-websocket/master/docs/generated/protocol.md)). This is policy: issue #545 asked in 2020 for a websocket video stream so OBS-web could show Program and Preview, and maintainer tt2468 closed it as not "worth the incredible amount of work" and "out of the scope of obs-websocket", belonging in its own plugin ([obs-websocket #545](https://github.com/obsproject/obs-websocket/issues/545)); five years later the only movement is a stalled single-frame `GetStreamScreenshot` PR (#1189) and bug #1257 on preview/program screenshot ambiguity ([PR #1189](https://github.com/obsproject/obs-websocket/pull/1189); [#1257](https://github.com/obsproject/obs-websocket/issues/1257)). Video therefore comes from a separate output, which is what DistroAV provides and what the owner has chosen.

Two adjacent facts shape the Vision Pro picture. SteamVR-style overlays are structurally impossible there: Valve's Steam Link beta for Vision Pro streams to a flat window and "doesn't include support for VR content" ([Road to VR](https://roadtovr.com/valve-steam-link-beta-vision-pro-vr-games)). And the one shipping app that does what the Mac-host mode wants, **Spatial Render**, streams a Mac's screen to Vision Pro "using the Remote Immersive Rendering feature in macOS Tahoe and visionOS 26" at a claimed "2.5K@90Hz per eye" ([App Store](https://apps.apple.com/mx/app/spatial-render/id6751405237)). No public project uses Qt Quick 3D XR to control a desktop application, and Qt's 6.11 and 6.12 release posts contain no XR content at all ([Qt 6.12 LTS Released](https://www.qt.io/blog/qt-6.12-released)).

|---|---|---|---|---|
| OBS-SteamVR-Overlay | SteamVR, Windows | obs-websocket v5 | No | Live-surface scope and VR ergonomics; licence unstated |
| Desktop+, WayVR, OVR Toolkit | SteamVR/OpenXR | None (mirror the OBS window) | Only as mirrored desktop | Capture/composite plumbing; WayVR runs on Steam Frame |
| OBS Controller, OBS Blade, CTD Live Mobile | iPad apps, run on Vision Pro | obs-websocket | Blade and CTD: screenshot polling | UX floor to try on a Vision Pro today |

## Qt Quick 3D XR is a technology preview that cannot host Widgets, and visionOS is its most fragile platform

The rendered Qt 6.12.0 documentation stamps the module "This module is in technology preview and is subject to change" and every one of its 16 QML types "Status: Technology preview", two years after it arrived in Qt 6.8 ([Qt Quick 3D Xr QML Types](https://doc.qt.io/qt-6/qtquick3d-xr-qmlmodule.html); [XrItem](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xritem.html)). Qt 6.12 LTS shipped on **30 September 2026** with five years of maintenance ([Qt 6.12 LTS Released](https://www.qt.io/blog/qt-6.12-released); [Qt LTS](https://www.qt.io/development/qt-framework/qt-lts)). The API has churned (`hand` deprecated for `controller` in 6.10; `multiViewRenderingEnabled` read-only since 6.9), and the per-release additions decide the baseline: 6.11 added OpenGL desktop Linux support for Monado, Xlib and Wayland, **Popup and Menu support inside `XrItem`** and OpenXR 1.1.49 headers ([What's New in Qt 6.11](https://doc.qt.io/qt-6/whatsnew611.html)); 6.12 added a mono view configuration and bundles OpenXR SDK **1.1.61** ([What's New in Qt 6.12](https://doc.qt.io/qt-6/whatsnew612.html); [6.12.0 release note](https://code.qt.io/cgit/qt/qtreleasenotes.git/about/qt/6.12.0/release-note.md)). Before 6.11, Qt Quick Controls dropdowns and menus did not render on an XR panel, so if Qt is used anywhere in this project, **6.12.1 or later is the only sensible baseline**.

The module has two backends chosen at Qt build time, `if (VISIONOS) add_subdirectory(visionos) else () add_subdirectory(openxr)` ([CMakeLists.txt](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/CMakeLists.txt)). The platform page, titled "Supported Headsets", puts **Apple Vision Pro standalone, Meta Quest 3 standalone and Quest 3 PCVR on Windows in Tier One**, Quest 2 and HTC Vive PCVR on Linux in Tier Two, and warns that other OpenXR devices "may be functional too, but this is not verified by Qt" ([Supported Headsets](https://doc.qt.io/qt-6/qt3dxr-supported-platforms.html)). There is **no "Qt for visionOS" platform page** on doc.qt.io, no visionOS row in Qt's Supported Platforms table, and the Vision Pro quick-start's "supported versions" link points to an anchor that does not exist ([Supported Platforms](https://doc.qt.io/qt-6/supported-platforms.html); [Getting Started With Apple Vision Pro](https://doc.qt.io/qt-6/qt3dxr-quick-start-guide-applevisionpro.html)); the only version floor is a qtbase commit, "Bump minimum requirement for visionOS to version 2" (June 2025) ([code.qt.io](https://code.qt.io/cgit/qt/qtbase.git/commit/?id=12e616dc0b3d0daca7f3e76cd167ba6315f111bc)). Steam Frame, SteamOS and Valve appear nowhere in Qt's docs; the only Valve references are "SteamVR OpenXR runtime" and "Steam Link" rows in the PCVR tested-configuration table ([PCVR](https://doc.qt.io/qt-6/qt3dxr-pcvr.html)).

On visionOS the guide is confirmed verbatim: "there is no binary build of Qt for visionOS", Apple Silicon is required, apps deploy through Xcode, and "visionOS supports applications transitioning between these two states [windowed and immersive], but this is not supported by QtQuick3D.Xr" ([Getting Started With Apple Vision Pro](https://doc.qt.io/qt-6/qt3dxr-quick-start-guide-applevisionpro.html)). Git history adds what the docs omit: "visionOS still requires static Qt builds, as the Swift entrypoint machinery has not yet been untangled" (May 2026) ([code.qt.io](https://code.qt.io/cgit/qt/qtbase.git/commit/?id=4fc36aa558b7b79bdf1171cd49c22398e885b1dd)), and the original port noted "there is currently no way to bring up QWindows", a limitation tracked by the still-open epic QTBUG-121781 "Modernize iOS window management" ([code.qt.io](https://code.qt.io/cgit/qt/qtbase.git/commit/?id=d5bf42f75b0ae35b7f02bb9211787ae1d44a98ba); [QTBUG-121781](https://bugreports.qt.io/browse/QTBUG-121781)). Passthrough is a launch-time decision: QTBUG-129736 is unresolved and says the only route today is a transparent background plus `UISceneInitialImmersionStyle = UIImmersionStyleMixed` in Info.plist, with "no sensible way to detect, report and/or change the mode at runtime" ([QTBUG-129736](https://bugreports.qt.io/browse/QTBUG-129736)). The tracker also shows how fragile the platform is: QTBUG-150753 "visionOS: Rendering broken" (P1, "None of the examples work correctly") was filed against the 6.12.0 RC on 23 September 2026 and fixed in 6.12.0/6.12.1, QTBUG-147559 (P1, apps do not start with 6.12 beta1) was fixed in Beta 2, and QTBUG-133524 notes the visionOS simulator has "no emulation of anchors, pass-through or multiview" ([QTBUG-150753](https://bugreports.qt.io/browse/QTBUG-150753); [QTBUG-147559](https://bugreports.qt.io/browse/QTBUG-147559); [QTBUG-133524](https://bugreports.qt.io/browse/QTBUG-133524)). These are the specific findings behind the project decision to keep Qt off the headset.

The 2D-UI story is what rules out a Widgets port. `XrItem` holds exactly one Qt Quick `Item` and scales it to a real-world rectangle: "the effect here is achieved by scaling the content item and not by rendering the content item at a higher resolution" ([XrItem](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xritem.html)); scene units are centimetres ([XR Input Example](https://doc.qt.io/qt-6/qtquick3d-xr-input-example.html)). Qt publishes no DPI or performance guidance for `XrItem`; the only official signal is a set of open P2 tickets, including QTBUG-132810, where an `XrItem`-hosted UI "leads to 2 FPS", and QTBUG-131645 on `Text.NativeRendering` rendering badly in an `XrView` ([QTBUG-132810](https://bugreports.qt.io/browse/QTBUG-132810); [QTBUG-131645](https://bugreports.qt.io/browse/QTBUG-131645)). Qt's "2D content in 3D" page describes only Qt Quick items as embeddable, and **Qt Widgets are mentioned nowhere** in the Qt Quick 3D or XR documentation ([Qt Quick 3D 2D in 3D](https://doc.qt.io/qt-6/qtquick3d-2d.html)). The project decision that follows is that **any Qt headset UI is a new QML shell, not a port**. The scale of what would not be ported was counted in this checkout: the `frontend/` tree is **88,669 lines** of C++ and Objective-C++, of which `OBSBasic` and its 27 partial files are 22,157 lines, `settings/` is 9,659, `dialogs/` is 7,117, and there are 36 `.ui` forms. The sync-friendly shape, whichever toolkit renders the headset UI, is to leave upstream `frontend/` and libobs untouched, build the immersive UI as a separate process, and generate source, filter and output settings UIs from the `obs_properties` data model instead of re-implementing dialogs. The owner can obtain a Qt small business licence covering Qt Quick 3D, Qt Quick 3D XR and Qt Virtual Keyboard; the purchase is held until the Steam Frame toolkit is decided, because the Phase 1 visionOS client contains no Qt.

The pieces a Qt PCVR shell would need are confirmed in the rendered docs: `XrVirtualMouse` maps a controller's forward vector to real `QMouseEvent`s with buttons and scroll ([XrVirtualMouse](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xrvirtualmouse.html)); `XrView.referenceSpace` defaults to `ReferenceSpaceLocal` but is forced to `LocalFloor` on visionOS, with a documented y-offset workaround ([XrView](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xrview.html)); and on visionOS Qt converts gaze-derived pinch events into left-button events only while a pinch is active, so there is no hover before selection, a behaviour visible only in source ([qquick3dxrinputmanager_visionos.mm](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/xr/quick3dxr/visionos/qquick3dxrinputmanager_visionos.mm)). On PCVR, QTBUG-133486 "XrView offset on windows" is an **open P1** tied to display scaling and QTBUG-146647 reports that the OpenXR `LOSS_PENDING` state is mishandled ([QTBUG-133486](https://bugreports.qt.io/browse/QTBUG-133486); [QTBUG-146647](https://bugreports.qt.io/browse/QTBUG-146647)).

Licensing is fully primary-sourced and now confined to the Steam Frame decision. Qt's licensing page lists Qt Quick 3D and Qt Virtual Keyboard among 14 modules available "under the GNU General Public License v3" rather than LGPL, and Qt Quick 3D XR ships inside Qt Quick 3D, banded "Commercial or GPLv3" ([Qt Licensing](https://doc.qt.io/qt-6/licensing.html); [Qt Quick 3D](https://doc.qt.io/qt-6/qtquick3d-index.html)); GPL-only modules require "your application or device to be licensed under GPL, as well", and store terms "may or may not be compatible with distributing applications under LGPL or GPL licenses" ([Obligations of the GPL and LGPL](https://www.qt.io/licensing/open-source-lgpl-obligations); [Qt Open Source Licensing FAQ](https://www.qt.io/faq/qt-open-source-licensing)). OBS is GPLv2 "or any later version" ([COPYING](https://github.com/obsproject/obs-studio/blob/master/COPYING)), so a Qt Quick 3D build combined with OBS code is GPLv3 overall unless the commercial licence is used; Apple's own position on GPLv3 apps was not found on an Apple page. The native visionOS client sidesteps all of this because it contains neither libobs nor Qt, so the Phase 0 licence decision concerns only the headset app's own code.

## visionOS gives a remote client everything it needs and a resident OBS almost nothing

Capture is where visionOS stops being an OBS platform, with one correction from the first draft. Apple's ScreenCaptureKit page now lists **visionOS 27.0**, says it "replaces ReplayKit for screen streaming and mirroring. A broadcast extension is no longer necessary", routes selection through `SCContentSharingPicker`, and pairs with a new `screen-capture` background mode on visionOS ([ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit); [Configuring background execution modes](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes)). What it exposes on visionOS is undocumented; the enterprise entitlement `com.apple.developer.screen-capture.include-passthrough` (visionOS 2.0+) still exists, and an Apple engineer's forum answer that ReplayKit frames without it "contain a black background instead of passthrough" is the only statement on the composite ([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.screen-capture.include-passthrough); [Apple Forums 757738](https://developer.apple.com/forums/thread/757738)). The main camera, passthrough-composited capture and the compute-headroom entitlement are **Enterprise APIs**, "eligible for business use only" and distributable only in-house or through Apple Business Manager ([Apple enterprise APIs](https://developer.apple.com/documentation/visionos/building-spatial-experiences-for-business-apps-with-enterprise-apis)). Background execution is the iOS set (`audio`, `voip`, `bluetooth-central`, `screen-capture`, `fetch`, `remote-notification`, `processing`), with nothing to wake an app on network traffic ([Configuring background execution modes](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes)). The M5 Vision Pro has 16 GB of unified memory, **Wi-Fi 6 (802.11ax)**, Bluetooth 5.3, refresh rates of 90 to 120 Hz, "up to 2.5 hours of general use" and a 0 to 30 °C operating range ([Apple Support 125436](https://support.apple.com/en-us/125436)). A resident libobs could ingest network sources and the mic but could not capture other apps, run in the background or sustain encoding; the remote design makes all of that moot, because the headset decodes NDI and sends JSON.

Input is better than the first draft said, and it anchors the project's input model. Apple's M5 tech specs list "Supported Input Accessories: Keyboards; Trackpads and mouse devices (Mouse support requires visionOS 2 or later); Game controllers" and "Supported Spatial Accessories: Logitech Muse; PlayStation VR2 Sense controller" ([Apple Support 125436](https://support.apple.com/en-us/125436)); the user guide warns that "Not all apps are compatible with spatial accessories" ([Apple Vision Pro User Guide](https://support.apple.com/guide/apple-vision-pro/connect-spatial-accessories-tan7a3f2c9d3/visionos)). visionOS 26 introduced the Sense controller with "high-performance motion tracking in 6 degrees of freedom, finger touch detection, and vibration support", sold by Apple from 11 November 2025 at $249.95 ([Apple Newsroom, June 2025](https://www.apple.com/newsroom/2025/06/visionos-26-introduces-powerful-new-spatial-experiences-for-apple-vision-pro/); [Apple Newsroom, October 2025](https://www.apple.com/newsroom/2025/10/apple-vision-pro-upgraded-with-the-m5-chip-and-dual-knit-band/)); visionOS 27 adds custom tracked accessories through the Game Controller framework, with hands tracked at 90 Hz ([WWDC26 287](https://developer.apple.com/videos/play/wwdc2026/287/)), and a visionOS 26 note records that while a controller is tracked, ARKit hand tracking for that hand updates at only 1 Hz ([visionOS 26 Release Notes](https://developer.apple.com/documentation/visionos-release-notes/visionos-26-release-notes)). The project decision is that **gaze-and-pinch is the primary and sufficient input on Vision Pro**; the owner's PSVR2 Sense controllers are an optional enhancement via GameController and ARKit accessory anchors that duplicates on-panel controls and is never required. Because Steam Frame has only controllers, the shell needs one pointer-and-action abstraction with two backends: gaze plus pinch, and tracked-controller ray plus buttons.

Window rules favour a native app. An app with `UIApplicationSupportsMultipleScenes` "can display any number of windows together with an immersive space", only one immersive space may be open system-wide, and opening one "hides all windows that belong to other apps" ([Presenting windows and spaces](https://developer.apple.com/documentation/visionos/presenting-windows-and-spaces)). A SwiftUI app can therefore float a scenes panel, a mixer, a transport strip, generated settings forms and video windows in the Shared Space, add a volume for a multiview wall, and offer an optional immersive stage, with the operator's other apps still visible; an immersive-only Qt app could do none of that. The project decision is that the app **must not rely on Mac Virtual Display** or any other mirror of the desktop UI: everything the desktop app can control, from source properties and filter settings during a show to plugin installation and the auto-config wizard between shows, must be reachable in the headset app itself. That requirement is what makes the parity section below load-bearing rather than aspirational.

Debugging needs hardware, but less than the first draft implied: the visionOS 26 Simulator now handles CompositorServices progressive immersion and hover effects ([visionOS 26 Release Notes](https://developer.apple.com/documentation/visionos-release-notes/visionos-26-release-notes)) but drives gaze and pinch with a mouse, so hand tracking, Sense controllers and Wi-Fi behaviour need the device. The second-generation Developer Strap (press-reported at $299, up to 20 Gb/s; Apple's page is behind a sign-in) is worth budgeting ([UploadVR](https://www.uploadvr.com/apple-developer-strap-upgrade/)). visionOS 27.0 shipped on 14 September 2026 ([MacRumors](https://www.macrumors.com/2026/09/14/apple-releases-visionos-27/)). Because the client is a SwiftUI package, the project decision is also to build it for macOS for desk debugging, which keeps the daily loop on a Mac against a local OBS.

## Steam Frame is a controller-only Windows PCVR target, and the Mac path is RemoteImmersiveSpace or nothing

Valve's store page specifies dual **2160 by 2160 LCDs at "72-144Hz refresh rate (144Hz experimental)"**, 16 GB LPDDR5X, "4x outward facing monochrome cameras for controller and headset tracking", two interior eye-tracking cameras for foveated streaming, monochrome passthrough, field of view "up to 110 degrees", a Wi-Fi 6E wireless adapter in the box, controllers with "capacitive finger sensing", and developer kits requested "in your Steam partner dashboard. Supplies are limited" ([Steam Frame](https://store.steampowered.com/hardware/steamframe)). Neither the store page nor the Steamworks input page, which lists "capacitive finger tracking, and 6-DOF spatial tracking", mentions camera-based hand tracking ([Steamworks: Steam Frame Input](https://partner.steamgames.com/doc/steamhardware/steamframe/input)), so **controllers are the only pointer on Steam Frame**. The reservation lottery was randomised on 17 September 2026 with purchase emails from 18 September ([Steam Frame](https://store.steampowered.com/hardware/steamframe)); the price block is injected client-side and could not be read from Valve, press is near-unanimous on **$1,059 (256 GB) and $1,299 (1 TB)** while Gamers Nexus prints $1,049 for the 256 GB model, and the 9 October "by December or in 2027" shipping statement is secondary-sourced ([Engadget](https://www.engadget.com/2257150/valves-steam-frame-vr-headset-starts-at-1059-and-ships-with-half-life-alyx/); [vr.org](https://vr.org/steam-frame-release-date)). Gamers Nexus (23 September 2026) measured 46.1 ms click-to-photon over the adapter in its LDAT software test, but the figures to plan a VR UI around are its streamed Thumper numbers: **65.7 ms with multi-link, 68.4 ms adapter-only and 86.2 ms over Wi-Fi at 120 Hz, versus 56.5 ms running locally** ([Gamers Nexus](https://gamersnexus.net/pre-built-pc-handheld-pcs-peripherals/valve-steam-frame-vr-review-vs-meta-quest-3-privacy-latency)).

The PCVR path needs no Steam Frame-specific code. Valve's Steamworks docs promise "full compatibility with SteamVR and OpenXR", support "Windows and Linux PC titles as well as native ARM64 and Android-based APKs", tell custom engines to use OpenXR and target "Android 10 or Linux Arm64" for on-device builds, note that controllers "will show up to your games as emulating Oculus Touch" by default with a dedicated interaction profile, and document Developer Mode (ssh, adb, rdp) ([Steamworks: Steam Frame](https://partner.steamgames.com/doc/steamhardware/steamframe); [Custom Engines](https://partner.steamgames.com/doc/steamhardware/steamframe/engines/custom); [Setup](https://partner.steamgames.com/doc/steamhardware/steamframe/setup)). Qt's PCVR page lists the SteamVR OpenXR runtime among its tested configurations and recommends D3D12 or Vulkan ([PCVR](https://doc.qt.io/qt-6/qt3dxr-pcvr.html)). The host-OS caveat is **unverified from Valve**: the "wireless adapter streaming is Windows-only, Linux partial" statement comes from a secondary report of a Valve support article that could not be located, while Valve's Linux dongle troubleshooting script and a SteamOS 3.9 / kernel 7.2 requirement are reported by GamingOnLinux ([GamingOnLinux](https://www.gamingonlinux.com/2026/09/valve-made-a-steam-frame-dongle-troubleshooting-script-for-linux-gamers/)). The planning assumption stands: Windows primary, Linux secondary, libobs on the same PC. A native on-headset build, which community ports show is possible against the on-device SteamVR OpenXR runtime ([quakevr PR 75](https://github.com/vittorioromeo/quakevr/pull/75)), would mean cross-compiling libobs for aarch64 SteamOS with unverified capture and encoders, a different project.

macOS has no OpenXR. Valve's statement of 1 May 2020 reads "SteamVR has ended OSX support so our team can focus on Windows and Linux" ([9to5Mac](https://9to5mac.com/2020/05/01/valves-steamvr-ends-support-for-macos/)), and Qt's macOS Metal OpenXR backend exists "to support running in Meta XR Simulator on macOS" ([What's New in Qt 6.9](https://doc.qt.io/qt-6/whatsnew69.html)). The only Apple-sanctioned path from a Mac to a headset is `RemoteImmersiveSpace`, a SwiftUI scene available on macOS 26.0, "a container for compositor content that your macOS app presents on a user's chosen visionOS device"; the remote device "hides all other visible apps" while it is open ([RemoteImmersiveSpace](https://developer.apple.com/documentation/swiftui/remoteimmersivespace)). WWDC25 session 294 states "On Mac, only the progressive and full immersion styles are supported", that the Mac hosts the CompositorLayer and ARKit session, that "any input device connected to your Mac" works including gamepads, and that the motivation is rendering "without being constrained by the power usage of Vision Pro" ([WWDC25 294](https://developer.apple.com/videos/play/wwdc2025/294/)); a Vision Pro engineer adds that RealityKit is unavailable there, so rendering is Metal 3 or 4 ([Apple Forums 787528](https://developer.apple.com/forums/thread/787528)). The release notes add that a session can run over "wired USB connection" as well as Wi-Fi, that Apple-silicon Macs could show "video stalls, blurry content, and black rendering on the sides" with the `renderQuality` API as the lever, and that "If you port an app using Xcode template or Metal 4 with ProgressiveImmersionStyle for macOS spatial rendering, the app will crash on macOS" (workaround: Full) ([visionOS 26 Release Notes](https://developer.apple.com/documentation/visionos-release-notes/visionos-26-release-notes)); visionOS 27 fixed a device-discovery failure ([visionOS 27 Release Notes](https://developer.apple.com/documentation/visionos-release-notes/visionos-27-release-notes)). **Apple publishes no latency, resolution, refresh or bitrate figure for RemoteImmersiveSpace.**

For completeness, since the product must not depend on it: Mac Virtual Display shows only the Mac's main display, connects to one Mac at a time, needs macOS 14, and reaches Standard 5120 by 2880 on Apple silicon, Wide 6720 by 2880 and Ultrawide **10240 by 2880 pixels** (Wide and Ultrawide need Apple silicon, macOS 15.2 and visionOS 2.2) ([Apple Support 118521](https://support.apple.com/118521)), at up to 120 Hz on the M5 model ([Apple Newsroom](https://www.apple.com/newsroom/2025/10/apple-vision-pro-upgraded-with-the-m5-chip-and-dual-knit-band/)). It is Mac-only, flat, undocumented for latency, and a visionOS 26 bug-fix note is the only evidence it has ever run alongside a `RemoteImmersiveSpace` ([visionOS 26 Release Notes](https://developer.apple.com/documentation/visionos-release-notes/visionos-26-release-notes)); the owner has ruled it out as a dependency.

One more route reuses a PCVR build. visionOS 26.4 added the `FoveatedStreaming` framework, which streams an OpenXR application from a host running the NVIDIA CloudXR 6.0 runtime ([Foveated Streaming](https://developer.apple.com/documentation/foveatedstreaming); [WWDC26 286](https://developer.apple.com/videos/play/wwdc2026/286/)); NVIDIA's requirements put the host on **Windows 10/11 or Ubuntu 22.04+, x86-64 only**, with specific Blackwell or Ada GPUs (RTX 5090/5080, RTX 4090 series, RTX Pro and Ada workstation parts, L40/L40S), so no Mac is possible ([CloudXR Runtime Requirements](https://docs.nvidia.com/cloudxr-sdk/latest/requirement/runtime_req.html)).

## OBS already exposes the control bus, DistroAV already exposes the video, and one small plugin closes the gap

The OBS frontend is a single in-process Qt 6 Widgets application: `OBSApp : QApplication` creates `OBSBasic : OBSMainWindow : QMainWindow`, the frontend links exactly `Qt6 Widgets Network Svg Xml` ([ui-qt.cmake](https://github.com/obsproject/obs-studio/blob/master/frontend/cmake/ui-qt.cmake)), and a tree-wide grep for QML or Qt Quick returns nothing. Preview video never passes through Qt: `OBSQTDisplay` hands `winId()` to libobs, which renders into that swap chain on its own graphics thread ([OBSQTDisplay.cpp](https://github.com/obsproject/obs-studio/blob/master/frontend/widgets/OBSQTDisplay.cpp)), and the live docs say displays need "a native window handle or identifier to draw on" ([docs.obsproject.com/frontends](https://docs.obsproject.com/frontends)). `obs-frontend-api` is a shared library of roughly **93 documented functions** (105 prototypes in the header) forwarding to an in-process callbacks object, covering scenes, transitions, T-bar, studio mode, outputs, profiles, scene collections, docks, undo/redo and screenshots ([reference-frontend-api](https://docs.obsproject.com/reference-frontend-api); [obs-frontend-api.h](https://github.com/obsproject/obs-studio/blob/master/frontend/api/obs-frontend-api.h)); the Canvas API "should be considered unstable" and plugins using it should "proceed with great caution" ([reference-canvases](https://docs.obsproject.com/reference-canvases)). `obs_get_main_texture()`, `obs_render_main_texture_src_color_only()` and `obs_add_raw_video_callback2()` are exported from `libobs/obs.h` with **no entry in the public reference** ([obs.h](https://github.com/obsproject/obs-studio/blob/master/libobs/obs.h)); they matter only for the later Mac immersive mode, where libobs's Metal texture is consumed in-process.

obs-websocket is the control bus. It is bundled since OBS 28 and listens on port 4455 ([OBS KB: Remote Control Guide](https://obsproject.com/kb/remote-control-guide)); the protocol authenticates with a salted SHA-256 challenge, supports JSON or MsgPack, frame-synced request batches (`SerialFrame`), bitmask event subscriptions with high-volume events such as the 50 ms `InputVolumeMeters` opt-in, and request categories spanning General, Config, Sources, Canvases, Scenes, Inputs, Transitions, Filters, Scene Items, Outputs, Stream, Record, Media Inputs and Ui ([protocol.md](https://raw.githubusercontent.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)). OBS 32.1.0 (11 March 2026) added "partial support for Canvases to obs-websocket" and WebRTC simulcast ([32.1.0](https://github.com/obsproject/obs-studio/releases/tag/32.1.0)); OBS 33 stops starting the server in Safe Mode ([33.0.0-rc3 notes](https://newreleases.io/project/github/obsproject/obs-studio/release/33.0.0-rc3)). What the protocol does not carry is the thing a generated settings UI needs most: per the protocol document it exposes an input's settings, default settings and the item lists of list-type properties (`GetInputSettings`, `SetInputSettings`, `GetInputDefaultSettings`, `GetInputPropertiesListPropertyItems`), but **not the full `obs_properties` schema** (property types, ranges, steps, visibility and group structure) that OBS's own property dialogs are generated from. The protocol's hotkey requests are "as-is" with no support guarantee, and it has no request for encoder settings, hotkey bindings or advanced audio configuration.

Video is NDI, by owner decision, because many OBS workflows already use it and because the outputs already exist. DistroAV (formerly OBS-NDI) provides an NDI Source, an NDI Output and an "NDI Filter/Dedicated Output" per source, requires "OBS v31.1.1 or higher" and "NDI Runtime v6.3 or higher" on Windows, macOS and Linux ([DistroAV README](https://raw.githubusercontent.com/DistroAV/DistroAV/master/README.md)), and its two program-level outputs are first-class OBS outputs: `NDI Main Output` and `NDI Preview Output`, kind `ndi_output`, where "Both outputs are always created when OBS starts, including when they are disabled" and "The Preview Output never carries audio", each controllable over obs-websocket's generic output requests ([DistroAV wiki](https://github.com/DistroAV/DistroAV/wiki/Controlling-DistroAV-outputs-with-obs‐websockets); [wiki Home](https://github.com/DistroAV/DistroAV/wiki)). Its latest release is 6.2.2 (13 October 2026), and the host requirement for this project is therefore stock OBS 31.1.1 or newer with bundled obs-websocket, DistroAV and NDI Runtime 6.3 or newer: **no custom video plugin**. On the headset, the NDI SDK release notes record "Added visionOS support to Apple SDKs" in NDI 6.2 (June 2025) and "Added missing NDI receiver advertiser API symbols to the visionOS library" in 6.3.2 (April 2026), and the platform page documents iOS finding, sending and receiving with the Bonjour service entry `_ndi._tcp.` in the app's Info.plist ([NDI SDK Release Notes](https://docs.ndi.video/all/developing-with-ndi/sdk/release-notes); [Platform Considerations](https://docs.ndi.video/all/developing-with-ndi/sdk/platform-considerations)); NDI's marketing page still says only "Windows, MacOS, Linux and more" ([NDI SDK](https://ndi.video/for-developers/ndi-sdk/)). Discovery also needs the standard iOS-family local-network privacy permission, and NDI's licence tiers separate commercial from personal use. The multiview benefit is structural: any NDI source on the network, cameras and other machines included, becomes a tile, not only OBS.

Bandwidth and latency are the risks to plan around. The Vision Pro is Wi-Fi 6 only ([Apple Support 125436](https://support.apple.com/en-us/125436)); full-bandwidth 1080p60 NDI is on the order of 125 Mbps per stream and the SDK offers a lowest-bandwidth "proxy" receive mode around 640 px wide (both figures are NDI's general guidance, not measured in this research), so the plan is proxy mode for every multiview tile and full bandwidth only for the selected Program monitor, a dedicated 5 GHz access point for the headset, and congested Wi-Fi named as a known failure mode with visible degradation rather than silent loss. No primary source gives an NDI-to-headset latency; LAN NDI is roughly a frame plus network, DistroAV publishes no figures, and the OBS forum carries both a 120 to 140 ms report and drift reports (about 250 ms growing to seconds in one sync mode, 40 ms per 10 minutes in another) against DistroAV ([OBS forum](https://obsproject.com/forum/threads/distroav-network-audio-video-in-obs-studio-using-ndi%C2%AE-technology.69240/page-24)). The app therefore measures and displays its own latency, offers reconnect, and the Phase 0 test plan includes a timecode-based glass-to-glass measurement. **WebRTC/WHIP is the documented WAN alternative**, not built in Phase 1: OBS's `whip_output` measured "~120 Milliseconds from Broadcaster to Playback" in its original PR ([PR #7926](https://github.com/obsproject/obs-studio/pull/7926)), LiveKit's Swift SDK officially "supports macOS, tvOS, and visionOS" ([LiveKit](https://docs.livekit.io/transport/sdk-platforms/swift.md)) while the stasel WebRTC xcframework fails to build for visionOS ([Swift Package Index](https://swiftpackageindex.com/builds/C952AB2E-BCF6-4781-89C7-92CD36926F26)), and it works off-LAN with signaling at a fraction of NDI's bitrate.

The companion plugin in this fork is the piece that turns a remote into a parity client, and its design is a project decision. obs-websocket's plugin API (`lib/obs-websocket-api.h`, API version 3) lets other OBS plugins register a vendor name and named requests from `obs_module_post_load()` and emit vendor events over the same socket, reached by clients through `CallVendorRequest` and `VendorEvent`; the mechanism and its limits are detailed in the upstreaming track below ([obs-websocket-api.h](https://raw.githubusercontent.com/obsproject/obs-websocket/master/lib/obs-websocket-api.h)). A small plugin, plain C against libobs with no Qt, registers a vendor namespace that serves full `obs_properties` schemas for sources, filters, transitions, outputs and encoders so the headset can generate settings forms; emits tally and selection events; handles device pairing (a QR code carrying host, port and a pairing token, as ProducerPad does); and auto-enables DistroAV's Main and Preview outputs and per-source NDI filters on request. It touches neither `frontend/` nor libobs, loads as an ordinary module, and the OBS 33 loader overhaul changes third-party locations on **Windows (and Linux packaging) only**, "Plugin locations on macOS have not been changed" ([OBS KB: Legacy plugin locations](https://obsproject.com/kb/legacy-plugin-locations)), so the fork's upstream diff is one plugin directory.

The OBS project's release facts bound both pieces. The latest stable is **32.2.2 (14 August 2026)**, which supports macOS 13.0 and newer ([obsproject.com/download](https://obsproject.com/download)); 33.0.0 is at RC3 (20 October 2026). OBS 33 makes Qt 6.10 the minimum as policy, PR #13969 "Qt 6.10 is the minimum supported Qt version now", while CMake still has no version argument, requires FFmpeg 8.0 and updates CEF from 127 to 150 ([PR #13969](https://github.com/obsproject/obs-studio/pull/13969)); OBS's binaries ship Qt 6.11.1 from obs-deps 2026-08-26 ([qt6.zsh](https://raw.githubusercontent.com/obsproject/obs-deps/2026-08-26/deps.qt/qt6.zsh)). OBS 32.0 (22 September 2025) added "custom OBS widgets in preparation for larger UI updates" and the experimental Metal renderer ([OBS 32.0 release notes](https://obsproject.com/blog/obs-studio-32-0-release-notes)), which OBS's blog says "is explicitly marked as 'Experimental'" because of "the way its preview rendering had to be implemented for now" ([How OBS Adopted Metal](https://obsproject.com/blog/obs-studio-gets-a-new-renderer)); the default renderer on Apple Silicon remains OpenGL in 33.0-rc3. There is no sign of a Qt Quick migration upstream, and libobs's Apple code has no `TARGET_OS_VISION` conditionals, so the remote design is also the upstream-compatible one.

## Full control parity is reachable in four tiers, and the Settings dialog is the hard one

The owner's requirement is parity of capability with the desktop app, not parity of screens. The design that delivers it is a generated-form engine driven by property schemas for the long tail of dialogs, with hand-built spatial panels reserved for the live surface: the Program and Preview wall and multiview, the mixer, the scene and source lists, transitions, and outputs. The table below sorts every desktop capability into the channel that provides it; request names are quoted only where the protocol document already cited above lists them, and other capabilities are described by category.

| Tier | Channel | Covers | Notes |
|---|---|---|---|
| 1 | obs-websocket, native | Scenes and scene collections; sources and inputs; scene items and transforms (`SetSceneItemTransform`); filters (full CRUD, order, enabled, settings); transitions and their settings and duration (`SetCurrentSceneTransition`); studio mode and T-bar (`SetStudioModeEnabled`, `TriggerStudioModeTransition`, `SetTBarPosition`); stream, record, replay buffer and virtual camera (`StartStream`, `StartRecord`, `PauseRecord`, `SplitRecordFile`, `CreateRecordChapter`, `StartVirtualCam`); audio volume, mute, monitoring and sync offset, with `InputVolumeMeters` at 50 ms; hotkey triggering (`TriggerHotkeyByName`, documented "as-is"); projectors (`OpenVideoMixProjector`, `OpenSourceProjector`); screenshots (`GetSourceScreenshot`); profiles; video settings (`GetVideoSettings`), stream service settings, record directory and arbitrary profile parameters in the Config category; stats (`GetStats`); media input control (`TriggerMediaInputAction`); canvases (partial, since 32.1) and WebRTC simulcast | Everything on this row is in the protocol document ([protocol.md](https://raw.githubusercontent.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)); it is most of what an operator touches during a show |
| 2 | Companion plugin vendor requests over the same socket | Full `obs_properties` schemas for sources, filters, transitions, outputs and encoders; stream and record encoder settings, which live in per-profile JSON files rather than the websocket API; hotkey binding configuration; audio device and advanced-audio configuration; multiview and projector configuration; anything reachable only through `obs-frontend-api` in-process | Plain C against libobs and `obs-frontend-api`; the vendor-request mechanism (API v3, synchronous `obs_data_t` callbacks, no streaming) is confirmed from the obs-websocket header and server source and is what Advanced Scene Switcher, Aitum and StreamUP ship on |
| 3 | Settings dialog apply semantics | Output, video and audio settings applied the way the desktop applies them | Writing config is easy; applying it requires mirroring the frontend's apply order (video reset, audio reset, output rebuild) from the 9,659-line `settings/` module, which is upstream-churn exposure. Scope output, video and audio first because they are show-critical; treat the remainder as config writes effective on next launch. This is the main upstream-sync risk in the plan |
| 4 | Desktop-app-level features | Plugin installation and the plugin manager, the auto-configuration wizard, scene collection importers, remux, update checks, log upload, theme editing, service chat docks and custom browser docks | All in scope by owner decision; sorted below by the kind of work each needs: portable logic the companion plugin hosts, config writes that need a frontend hook to apply live, and filesystem-plus-restart operations |

Two libobs facts fix the shape of Tier 3. The Frontends documentation says video "can be reconfigured by calling obs_reset_video() as long as no outputs are active" and audio "is not able to be reset once initialized; libobs must be fully shutdown in order to reconfigure audio settings" ([docs.obsproject.com/frontends](https://docs.obsproject.com/frontends)), so the headset must surface the same "stop outputs first" and "restart required" states the desktop shows, and the companion plugin must drive the apply through `obs-frontend-api` (`obs_frontend_reset_video` and the output handlers) rather than write config and hope. Encoder settings are the other trap: the desktop reads and writes them as per-profile JSON that the websocket never sees, so the plugin exposes them with their encoder `obs_properties` schema and the generated form edits them like any source. The generated-form engine itself is the single most reusable component in the project: it turns the 36 `.ui` forms and 7,117 lines of dialogs the desktop hand-maintains into one renderer over a schema, and it is the same engine whichever toolkit the Steam Frame client ends up using.

Tier 4 is in scope by the owner's third decision: **there is no desktop-only tier**, and the useful distinction is what kind of work each feature needs. The first group is portable logic the companion plugin can host directly because it has no UI dependency: the scene collection importers are self-contained converter code under `frontend/importers` (`classic.cpp`, `sl.cpp`, `studio.cpp`, `xsplit.cpp`; local checkout), remux is FFmpeg muxing behind `frontend/dialogs/OBSRemux.cpp` (local checkout), log upload and update checks are plain HTTP flows, and the auto-configuration wizard's bandwidth and encoder tests live under `frontend/wizards` (`AutoConfig*.cpp`, `TestMode.hpp`; local checkout) and can be extracted or reimplemented without Qt and driven by vendor requests. The second group is config writes that need a frontend hook to apply live: theme selection and plugin enable/disable are config changes the desktop applies through private frontend code, and the public `obs-frontend-api` offers only `obs_frontend_is_theme_dark()` on the theme side ([obs-frontend-api.h](https://github.com/obsproject/obs-studio/blob/master/frontend/api/obs-frontend-api.h)), so from the headset they take effect on next launch unless small frontend-API additions land upstream (a set-theme or reload-theme call, a reload-docks call), which ties them to the upstreaming track below. The third group is filesystem and restart operations: plugin installation is unpacking into the platform plugin folder plus an OBS restart, and because OBS 33 moved the Windows (and Linux packaging) plugin paths while "Plugin locations on macOS have not been changed" ([OBS KB: Legacy plugin locations](https://obsproject.com/kb/legacy-plugin-locations)), the companion plugin resolves paths per platform and the headset can request a restart.

Chat docks stay in scope and must obey the desktop configuration. In the local checkout, custom browser docks are persisted in the user config as JSON under `BasicWindow/ExtraBrowserDocks` (title plus URL), read and written in `frontend/widgets/OBSBasic_Browser.cpp` and `frontend/docks/YouTubeAppDock.cpp` and edited through `frontend/utility/ExtraBrowsersModel.cpp`; the Twitch, YouTube and Restream chat, info and feed docks are built in `frontend/oauth/TwitchAuth.cpp`, `YoutubeAuth.cpp` and `RestreamAuth.cpp` from the authenticated account's URL and opened through `cef->create_widget(..., panel_cookies)`, where `panel_cookies` is a per-profile CEF cookie manager created under `obs_profile_cookies/<Panels/CookieId>` (local checkout, `frontend/widgets/OBSBasic_Browser.cpp`). The consequence is clean on the data side and awkward on the session side: the companion plugin can publish the desktop's dock list, titles, URLs, visibility and layout to the headset, which renders each in a `WKWebView`, and edits on either side write the same config; but **the CEF cookie store cannot be shared with a visionOS web view**, so the operator signs into Twitch, YouTube or Restream once inside the headset, and any dock that depends on the desktop's OAuth session state rather than a public URL needs the plugin to hand over a URL the headset can open on its own.

## Recommended architecture: native visionOS remote first, NDI plus obs-websocket, companion plugin in the fork, toolkits decided later

The architecture that survives the constraints and reflects the project decisions has three loosely coupled pieces. First, **OBS on the host stays stock plus two plugins**: upstream `frontend/` and libobs untouched, obs-websocket enabled, DistroAV installed with NDI Runtime 6.3+, and this fork's companion plugin registering vendor requests. Second, the **Vision Pro client is a native SwiftUI/RealityKit app** with no libobs and no Qt: an obs-websocket control layer, a vendor-request layer for schemas, tally and pairing, a generated-form engine for every settings surface, hand-built panels for the live surface, and an NDI receiver whose Program monitor runs at full bandwidth while every multiview tile runs in proxy mode. It lives in the Shared Space so the operator's other apps remain visible, offers an optional immersive stage, and is built for macOS from the same SwiftUI package for desk debugging. Third, a **pointer-and-action abstraction** with two backends: gaze plus pinch (primary, sufficient) on visionOS, and tracked-controller ray plus buttons for PSVR2 Sense on visionOS and for Steam Frame controllers later; Sense input only duplicates what the panels already offer.

Three engineering rules follow. Vision Pro has no hover before pinch, so targets stay at 60 pt or larger and nothing depends on hover. Network behaviour is instrumented from day one: the client shows measured feed latency and bitrate, degrades tiles before the Program monitor, and reconnects to obs-websocket, NDI sources and the vendor channel independently. And the client never contains GPL code (obs-websocket is a wire protocol, the NDI SDK is a vendor library under NDI's terms), so App Store, TestFlight and enterprise distribution are all open.

The **Steam Frame PCVR client decision is deferred** to its own phase and held open between three options, with the Qt small business licence held until then. Qt Quick 3D XR gives QML, a tested SteamVR OpenXR path on Windows and a codebase that could also build for Quest 3 (Tier One), at the cost of a technology-preview API, the open P1 Windows scaling bug, GPLv3 or the commercial licence, and a second implementation of the live surface. Godot is MIT-licensed, has first-class OpenXR, and Apple's WWDC26 session named it among engines with visionOS support ([WWDC26 287](https://developer.apple.com/videos/play/wwdc2026/287/)), which would make it the one toolkit that could cover Steam Frame, Quest and a future immersive Vision Pro stage. Raw OpenXR with a custom panel renderer is the OBS-SteamVR-Overlay route, cheapest to start and most expensive to grow a UI in. Whatever is chosen, the client runs on the Windows PC against SteamVR's OpenXR runtime, so Quest 3 over Steam Link or any Index-class headset is a full stand-in until a Frame arrives, and the control, vendor and generated-form layers port as protocol code.

The **Mac RemoteImmersiveSpace path becomes a later optional "immersive studio" mode**. It wins on monitoring fidelity (zero-copy, uncompressed Program on the same GPU as libobs, no NDI encode at all), on distribution (a Mac app, no review) and on keeping everything on the Mac; it loses on UI toolkit (Metal only, no SwiftUI or RealityKit, every control hand-rendered), on immersion (full or progressive only, hiding every other app, so nothing can sit on the real desk), on reach (Mac-only hosts while most OBS installs are Windows) and on maturity (first release in macOS 26, progressive crashed in Apple's template, no published latency). It starts with a bounded spike: composite a Qt Quick or SwiftUI-rendered texture into the `CompositorLayer` at text quality an operator can read, and establish whether Sense controller input and hover effects are forwarded to the Mac in that mode, which Apple's pages do not say. If both hold, the Mac app renders the studio from libobs's Metal texture and reuses the Phase 1 control, vendor and form layers in Swift.

The Qt-based single-codebase route remains documented as the alternative if the owner later wants one codebase across all three targets: a new QML shell over the same obs-websocket and vendor-request layers, with a `QSGTextureProvider` over libobs's native texture for hosted builds and an NDI decoder into `VideoOutput` as `Texture.sourceItem` for remote builds, rendered by `XrView` on headsets and `View3D` on the desktop. Its primary-sourced costs are a static from-source Qt build per visionOS release with 6.12.1 as the floor, immersive-only operation on Vision Pro with passthrough fixed at launch and no Shared Space coexistence with other apps, `XrItem` panels that scale rather than supersample, GPLv3 or a commercial seat for every contributor who builds the XR target, and a Swift Metal host for the Mac mode anyway. It buys shared QML across Steam Frame, Quest and Vision Pro and nothing else the native plan lacks.

|---|---|---|---|

### Upstreaming track

The vendor API the companion plugin depends on has now been read from source rather than inferred. `lib/obs-websocket-api.h` declares `OBS_WEBSOCKET_API_VERSION 3`; a plugin calls `obs_websocket_register_vendor()` and `obs_websocket_vendor_register_request()` "ALWAYS … ONLY VIA `obs_module_post_load()`", each request callback receives an `obs_data_t` request and fills an `obs_data_t` response, events leave through `obs_websocket_vendor_emit_event()`, and the header back-fills API version 1 when obs-websocket is absent, so nothing has broken since the vendor mechanism shipped in 5.0.0 ([obs-websocket-api.h](https://raw.githubusercontent.com/obsproject/obs-websocket/master/lib/obs-websocket-api.h)). Server-side, incoming messages are dispatched on obs-websocket's thread pool and `PerformVendorRequest` invokes the callback synchronously under shared locks, so vendor callbacks run off the UI and graphics threads and the plugin must marshal any libobs or frontend work itself ([WebSocketServer.cpp](https://github.com/obsproject/obs-websocket/blob/master/src/websocketserver/WebSocketServer.cpp); [WebSocketApi.cpp](https://github.com/obsproject/obs-websocket/blob/master/src/WebSocketApi.cpp)). On the wire, `CallVendorRequest {vendorName, requestType, requestData}` returns `responseData`, `VendorEvent` carries `{vendorName, eventType, eventData}` under the `Vendors` subscription, vendor requests take part in ordinary request batches, there is **no streaming**, and **no payload size limit is stated** anywhere in the protocol document ([protocol.md CallVendorRequest](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md#callvendorrequest)). The mechanism is the sanctioned extension point in practice: the maintainers closed #273 "Allow 3rd-party OBS plugins to expose RPC methods" as "basically done" with it ([#273](https://github.com/obsproject/obs-websocket/issues/273)), first-party obs-browser registers a vendor, and Advanced Scene Switcher, Aitum Vertical Canvas (21 requests), Aitum Stream Suite (32) and StreamUP (66 request names including deprecated aliases) all ship on it; StreamUP's requests cover scale filtering, show and hide transitions, blend method, mono downmix and open-properties dialogs, which are exactly the gaps still open upstream ([streamup.cpp](https://github.com/StreamUPTips/obs-streamup/blob/master/streamup.cpp); [vertical-canvas.cpp](https://github.com/Aitum/obs-vertical-canvas/blob/master/vertical-canvas.cpp)). DistroAV registers no vendor, so the companion plugin controls its outputs through the generic output requests.

The upstream evidence argues for patience and narrow scope. The tracker holds **86 open feature requests and 23 open PRs**, and every one of the headset client's gaps already has an open issue, most with zero maintainer comments: the property-schema request #1099 "GetInputSettingsSchema / GetSourceFilterSettingsSchema" (February 2023) and #1227 (opaque `Object` settings), advanced output settings #575 (2020, "Needs Research"), encoder selection #1288, audio monitoring devices #798 (where tt2468 proposed request names in 2021 and nothing followed), projector control #949 and #1301, scene collection import #1240, and scene-item show/hide transitions #906, where tt2468 wrote in 2022 "This is planned to be implemented as Get/SetSceneItemVisibilityTransition in a future version" and community pings through 2025 went unanswered ([#1099](https://github.com/obsproject/obs-websocket/issues/1099); [#906](https://github.com/obsproject/obs-websocket/issues/906); [#798](https://github.com/obsproject/obs-websocket/issues/798); [open feature requests](https://github.com/obsproject/obs-websocket/issues?q=is%3Aissue+is%3Aopen+label%3A%22Issue%3A+Feature+Request%22+sort%3Acreated-desc)). PRs implementing three of those gaps sit unreviewed: #1322 scene-item show/hide transitions (November 2025, no reviews), #1350 audio mono (August 2026), #1352 blend method (August 2026) ([PR #1322](https://github.com/obsproject/obs-websocket/pull/1322); [open PRs](https://github.com/obsproject/obs-websocket/pulls?q=is%3Apr+is%3Aopen+sort%3Acreated-asc)). No written scope policy exists; the maintainer statements on record are tt2468's "It is out of the scope of obs-websocket" on video streaming ([#545](https://github.com/obsproject/obs-websocket/issues/545)), PatTheMav's "a remote control client (what websockets is made for) should not futz around with canvases" and Warchamp7's note that "the use of name is going to be removed entirely in favor of UUIDs" on the canvas PR ([#1314](https://github.com/obsproject/obs-websocket/pull/1314)), and tt2468's "We need to do an RPC version bump in order to expose events from non-main canvases", which acknowledges rpcVersion 2 as the vehicle for breaking changes with no date ([#1331](https://github.com/obsproject/obs-websocket/pull/1331)). Capacity is the bottleneck: commits fell from 550 in 2021 to 22 in 2025 and 48 in 2026 to date, since 2024 essentially every commit is committed by tt2468 or RytoEX, and RytoEX wrote on a waiting PR "I am not familiar enough with websockets or this PR to provide a review" ([commits](https://github.com/obsproject/obs-websocket/commits/master); [#1229](https://github.com/obsproject/obs-websocket/pull/1229)). Time to merge splits cleanly by shape: narrow parity requests on existing libobs objects from known contributors landed in **6 to 37 days** (#1265 profile fix, #1224 `cropToBounds`, #1187 hotkey context), while larger or conceptually new changes took **178 days** (#1314 canvases) to **10.5 months** (#1108), and outsider request PRs wait 28 to 49 months with no maintainer comment (#1189, #1229, #1023); no request-adding PR from a non-core author has merged since June 2024 ([#1187](https://github.com/obsproject/obs-websocket/pull/1187); [#1224](https://github.com/obsproject/obs-websocket/pull/1224); [#1265](https://github.com/obsproject/obs-websocket/pull/1265); [#1314](https://github.com/obsproject/obs-websocket/pull/1314); [#1189](https://github.com/obsproject/obs-websocket/pull/1189)).

The recommendation is therefore dual-track. Ship everything as vendor requests first, which is what StreamUP and Aitum do for the same gaps and what the companion plugin already plans. Then upstream a short list of narrow, UUID-first, non-breaking parity requests, each with the documentation comments that CI regenerates `protocol.md` from and a test script, timed before an OBS release's feature freeze: an `obs_properties` schema request closing #1099 and #1227 (novel, but it needs no OBS core change because libobs already exposes property enumeration), per-scene-item show and hide transitions closing #906 by supporting the drafted #1322, and blend method and mono downmix by supporting #1352 and #1350 ([Contributing Guidelines](https://github.com/obsproject/obs-websocket/wiki/Contributing-Guidelines); [docs/README.md](https://github.com/obsproject/obs-websocket/blob/master/docs/README.md)). Anything touching projectors, docks or multiview starts as an `obs-frontend-api` PR in obsproject/obs-studio, not as an obs-websocket PR: those items carry the "Requires OBS Changes" label on the websocket tracker, and the missing primitives are the ones the ideas board already requests, `obs_frontend_close_projector` (#2185) and `obs_frontend_list_docks` (#2752) ([Requires OBS Changes](https://github.com/obsproject/obs-websocket/issues?q=label%3A%22Requires+OBS+Changes%22+sort%3Aupdated-desc); [ideas #2185](https://ideas.obsproject.com/posts/2185/add-obs_frontend_close_projector-to-the-obs-frontend-api); [ideas #2752](https://ideas.obsproject.com/posts/2752/add-obs_frontend_list_docks-to-the-obs-frontend-api)). The reload-theme and reload-docks hooks from Tier 4 belong on that same obs-studio track. Program and Preview screenshots (#1130, #1189, #1257) stay on the vendor side: the stalled PR shows the naming and texture-reuse questions are unresolved and the headset does not need them once NDI carries both feeds.

Parallel development works as the team hoped, with the roles clarified: the control, vendor-request and generated-form layers are debugged on Macs and PCs against stock OBS, the SwiftUI client runs on macOS and in the visionOS Simulator for layout and against a real OBS for data, and the headset is needed early only for gaze-and-pinch feel, Sense tracking, Wi-Fi behaviour and thermal behaviour. The Steam Frame client is developed against whatever SteamVR headset is on hand, so the lottery does not gate it.

## Conclusion

The research reframes the project twice. The first draft's reframing holds: what was described as "an immersive port of OBS" is really the first non-Widgets OBS control surface, and the headset is incidental to most of the hard work. The second reframing comes from the owner's decisions read against the primary sources: the control surface does not need Qt, does not need a mirrored desktop, and does not need any new video code, because obs-websocket already carries nearly every live control, DistroAV already publishes Program and Preview as NDI outputs, and NDI's SDK already runs on visionOS. What OBS does not export is the schema its own dialogs are generated from, and that gap, closed by a vendor-request plugin in plain C, is what separates a scene switcher from a client with full control parity; the desktop-app-level features that remain are portable logic the same plugin can host, config writes awaiting two small upstream hooks, or a plugin folder and a restart.

The remaining risk is concentrated, not spread: Wi-Fi 6 bandwidth for NDI on the headset, which Phase 0 measures before anything is built on it, and the Settings dialog's apply semantics, which is the one place the headset must mirror frontend logic that upstream keeps changing. Everything else is sequenced so that nothing blocks Phase 1: the Steam Frame toolkit and the Qt licence are decided when a PCVR client is built against whatever SteamVR headset is available, and the Mac `RemoteImmersiveSpace` studio is promoted from "later" to "next" only if a short spike shows that hand-rendered UI is legible and controller input reaches the Mac. If the spike fails, the native remote already covers every operator task, and the Mac path stays a fidelity upgrade rather than a dependency.
