# Verification addendum: Qt XR / spatial-computing support (verified against primary Qt sources, 2026-10-22)

Method note: In this pass `doc.qt.io`, `bugreports.qt.io` (JIRA REST API `/rest/api/2/issue/...` and `/rest/api/2/search/jql`), `qt.io/blog`, `qt.io/licensing`, `qt.io/faq`, `wiki.qt.io`, `code.qt.io` (cgit) and `lists.qt-project.org` were all reachable via the sandbox proxy (curl), so every claim below is checked against the **rendered Qt 6.12.0 documentation** (page header "Qt 6.12.0", footer "© 2026 The Qt Company Ltd.") or the live tracker/blog. `WebFetch` still fails DNS for these hosts; `curl` through `$HTTPS_PROXY` works. ## 1. Qt Quick 3D XR status wording, supported platforms/tiers, "Qt for visionOS" platform page

### Takeaway
Confirmed: in the live Qt 6.12.0 docs the module and every XR QML type are stamped "Technology preview" ("This module is in technology preview and is subject to change" / "This type is in technology preview and is subject to change"), introduced in Qt 6.8. The platform page is titled **"Supported Headsets"** (not "Supported Platforms"), its tier lists match the original notes exactly, and **there is no "Qt for visionOS" platform page** on doc.qt.io (`visionos.html`, `qt-for-visionos.html`, `platforms.html` all 404; the qtdoc "Supported Platforms" page has no visionOS row). The only visionOS documentation is the Qt Quick 3D Xr "Getting Started With Apple Vision Pro" page, whose "supported versions" link points to a `#visionos-supported-versions` anchor that does not exist on the target page.

### Cited Findings

This module was introduced in Qt 6.8." — [Qt Quick 3D Xr QML Types (Qt 6.12.0)](https://doc.qt.io/qt-6/qtquick3d-xr-qmlmodule.html). ### Inferences
- The "technology preview" stamp is applied at type level in 6.12.0, so the report can say precisely: "every Qt Quick 3D Xr QML type is Technology Preview in Qt 6.12 LTS", not merely the module.
- Qt has no platform page, support tier, or version table for visionOS; the only official statement of requirements is the Vision Pro quick-start guide. The report should describe visionOS as "preliminary, source-build-only, documented solely within the Qt Quick 3D Xr module", citing the dangling "supported versions" link as evidence of how thin the platform documentation is.

### Gaps
- No Qt page states supported visionOS or Xcode versions; the minimum visionOS 2 requirement is only in a qtbase commit message (2025-06-20) and may have moved since.
- No roadmap statement about leaving Technology Preview was found in docs, blog or JIRA.

## 2. XrItem, XrVirtualMouse, XrView, XrRuntimeInfo rendered docs (input, scaling/DPI, Popup/Menu, performance, passthrough, referenceSpace)

### Takeaway
XrItem's rendered page confirms the scaling semantics verbatim and documents **nothing** about input handling, Popup/Menu support, DPI or performance (Popup/Menu support exists only as a 6.11 What's New bullet). XrView's page adds a **new visionOS referenceSpace workaround note** and documents the default `referenceSpace` as `ReferenceSpaceLocal`; its `multiViewRenderingEnabled` text is self-contradictory (header "default: true… read-only" vs body "It defaults to disabled"). XrVirtualMouse's rendered example still uses the `hand:` property that was deprecated in 6.10. XrRuntimeInfo is documented as auto-created by XrView and not manually creatable.

### Cited Findings
- **Original claim (XrItem definition, scaling note, properties).** **Verdict: CONFIRMED verbatim.** "The XrItem type is a Qt Quick 3D Node that represents a rectangle with width and height. It holds one Qt Quick Item, specified by contentItem, and scales it to fit… Any other children of the XrItem will be treated as normal children of a Node, and will not be scaled… Note that the effect here is achieved by scaling the content item and not by rendering the content item at a higher resolution." Properties documented: `automaticHeight` (default false), `automaticWidth` (default false), `color` (default "white"), `contentItem`, `height`, `manualPixelsPerUnit` (default false), `pixelsPerUnit`, `width`. Since Qt 6.8, inherits Node, Status "Technology preview". — [XrItem QML Type](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xritem.html)
- **Specific gap asked (XrItem input handling / Popup-Menu / DPI / performance notes).** **Verdict: COULD NOT VERIFY in XrItem docs — the page contains none of these topics.** The only Popup/Menu statement anywhere in the 6.12 docs is the What's New bullet "Added Popup and Menu support in XrItem through dedicated QQuickOverlay" — [What's New in Qt 6.11](https://doc.qt.io/qt-6/whatsnew611.html). The XR Input example is the only place that explains sizing: "since the unit size is one centimeter, those user interfaces will have to be scaled to be useful. The XrItem type provides a convenient way to do the scaling automatically by setting the physical size of the 3D item and the logical size of the 2D surface… set it to be 75 cm wide and 100 cm tall. Then add a rectangle as a content item, and set it to be 300 x 400 units… The 2D content is automatically scaled so it fills the XrItem." — [Qt Quick 3D - XR Input Example](https://doc.qt.io/qt-6/qtquick3d-xr-input-example.html). (This confirms the original "1 unit = 1 cm" claim from an official doc page rather than from source.)
- **Original claim (XrVirtualMouse description, properties, defaults).** **Verdict: CONFIRMED, with one precision.** "Maps 3D controller input to mouse input in 2D items… provides a way to interact with 2D user interfaces in the 3D scene." Properties: `enabled`, `leftMouseButton`, `middleMouseButton`, `rightMouseButton`, `scrollPixelDelta` (default 15), `scrollTimerInterval` (default 30 ms), `scrollWheelX`, `scrollWheelY` ("Scroll speed increases relative to distance from zero"), `source` ("normally set to an XrController. Mouse events are generated for the position where the forward vector of the source node intersects with a 2D item"), `view`. Inherits **Item** (not Node). The rendered usage example still reads `XrInputAction { id: rightTrigger; hand: XrInputAction.RightHand; actionId: [TriggerPressed, TriggerValue] }` — i.e. it uses the `hand` property that XrInputAction's own page lists under "Deprecated members" in favour of `controller` (since 6.10). — [XrVirtualMouse QML Type](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xrvirtualmouse.html); [XrInputAction QML Type](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xrinputaction.html)
- **Original claim (XrView properties/methods).** **Verdict: CONFIRMED, with corrections/additions:**
  - `referenceSpace` **default is `XrView.ReferenceSpaceLocal`** (original notes did not state the default). New note on the rendered page: "On visionOS, the reference space is always ReferenceSpaceLocalFloor and cannot be changed. This means that applications designed with ReferenceSpaceLocal will have their origin at floor level on visionOS, which can cause content to appear at an unexpected position. To handle this, applications can check the referenceSpace property at runtime and adjust the vertical position of their content accordingly. For example: `y: xrView.referenceSpace === XrView.ReferenceSpaceLocalFloor ? 130 : 0`".
  - `multiViewRenderingEnabled`: header says "[default: true] This is a read-only property… When not supported, the value will flip back to false" but the body still says "It defaults to disabled to ensure maximum compatibility. Developers are encouraged to verify… with multiViewRenderingEnabled set to true" — stale text contradicting the 6.9 change; the Multiview page is authoritative: "Multiview rendering is enabled by default, as long as the underlying graphics API supports it… disable… by setting the environment variable QT_QUICK3D_XR_DISABLE_MULTIVIEW to a non-zero value."
  - `fixedFoveation` default `XrView.HighFoveation`; "VisionOS-based devices perform dynamic, eye-tracked foveation; thus, the value of this property is ignored in practice. Other devices, such as the Meta Quest 3, only support fixed foveation".
  - `depthSubmissionEnabled` default false; "in some platforms, depth submission is implicit and cannot be disabled… An example of this is VisionOS."
  - `passthroughEnabled` / `passthroughSupported` have one-line docs only ("Holds whether passthrough is enabled for the XR view" / "Indicates whether passthrough is supported for the XR view"); the **only platform note on passthrough is for Meta Quest** (`com.oculus.feature.PASSTHROUGH` uses-feature). **There is no visionOS passthrough statement on the XrView page** — the "not supported at runtime on visionOS" behaviour in the original notes comes from source only.
  - Methods: `closestPointPick` (since 6.11), `processTouch` ("search for an XrItem, or a Model with a sourceItem texture, near position and send a virtual touch event"), `rayPick` (+ model overload since 6.11), `rayPickAll`, `setTouchpoint`, `touchpointState` (map keys grabbed/target/pressed/cursorPos/touchDistance, plus since 6.11 surfacePoint/normal/uvPosition/model). Signals `initializeFailed`, `sessionEnded`. `xrOrigin`: "An application can have multiple XrOrigins but only one can be active at a time… This property must be set for the scene to be rendered in XR."
  — [XrView QML Type](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xrview.html); [Multiview Rendering](https://doc.qt.io/qt-6/qt3dxr-multiview.html)
- **Original claim (XrRuntimeInfo: enabledExtensions, runtimeName, runtimeVersion, graphicsApiName).** **Verdict: CONFIRMED, plus:** "Note: This type is automatically created by an XrView, and it can not be manually created." `enabledExtensions` "may vary depending on the runtime implementation and can be empty." Inherits Item; status Technology preview. The description also mentions "whether multi-view rendering is supported" but no such property is listed (another doc inconsistency). — [XrRuntimeInfo QML Type](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xrruntimeinfo.html)
- **Original claim (XrHandModel has no content on Vision Pro; Meta needs HAND_TRACKING permission).** **Verdict: CONFIRMED.** "The Apple Vision Pro will overlay video of the user's hands directly, and the XrHandModel will not have any content." — [XrHandModel QML Type](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xrhandmodel.html)
- **Original claim (XrController poseSpace AimPose default "Used when aiming at something, such as with XrVirtualMouse", pokePosition).** **Verdict: CONFIRMED.** — [XrController QML Type](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xrcontroller.html)
- **Original claim (XrInputAction pinch actionIds; `hand` deprecated for `controller` in 6.10).** **Verdict: CONFIRMED.** Table rows "IndexFingerPinch — Thumb to index finger pinch gesture. Boolean" … "HandTrackingMenuPress — Hand tracking menu gesture. Boolean"; `controller : enumeration (since 6.10)`, `enabled : bool (since 6.9)`, and a "Deprecated members" link; example "react to either the right hand grip being pressed or to a right hand pinch gesture" uses `actionId: [SqueezePressed, SqueezeValue, IndexFingerPinch]`. — [XrInputAction QML Type](https://doc.qt.io/qt-6/qml-qtquick3d-xr-xrinputaction.html)
- **Original claim (multiview constraint on custom 2D shaders; multiview "reducing the GPU and especially the CPU load").** **Verdict: CONFIRMED verbatim.** — [Multiview Rendering](https://doc.qt.io/qt-6/qt3dxr-multiview.html)
- Performance/legibility tickets relevant to XrItem (all still open, see §4 for the full list): QTBUG-131581 "UI Performance Degradation When Using Qt Quick 3D.XR" (Reported, P2, 2024-11-26, Quest 3, OutrunXR demo); QTBUG-132810 "Using XrItem instead of using a qml item" (Reported, P2; an XrItem-hosted IVI UI "leads to 2 FPS" vs a Model+texture); QTBUG-131645 "Bad rendering of a Text with Text.NativeRendering in an XrView contentItem" (Open, P2); QTBUG-131600 "Allow contentItem of XrItem to have Window as well" (Suggestion, Reported) — [QTBUG-131581](https://bugreports.qt.io/browse/QTBUG-131581), [QTBUG-132810](https://bugreports.qt.io/browse/QTBUG-132810), [QTBUG-131645](https://bugreports.qt.io/browse/QTBUG-131645), [QTBUG-131600](https://bugreports.qt.io/browse/QTBUG-131600)

### Inferences
- The report can state as fact that Qt publishes no DPI, resolution, or performance guidance for XrItem; the open P2 tickets about XrItem frame-rate collapse and NativeRendering text are the only official signal, and they point to "use default (distance-field) text rendering" and "keep XrItem content lightweight" as practical rules.
- Because `referenceSpace` defaults to Local but is forced to LocalFloor on visionOS, an OBS shell must either set `ReferenceSpaceLocalFloor` everywhere or apply the documented runtime y-offset check; this is now an official Qt recommendation, not just an inference.

### Gaps
- Whether XrVirtualMouse emits hover (MouseMove without button) on visionOS remains undocumented; the XrView page has no visionOS input section at all.
- The XrView page's multiview wording is contradictory; the report should cite the Multiview page and the 6.9 What's New instead.

## 3. Qt for visionOS: build/deploy constraints, immersion modes, QTBUG-121781, tracker status

### Takeaway
The Vision Pro guide is confirmed verbatim (source-build-only, Apple Silicon, Xcode deployment, no windowed/immersive transition in QtQuick3D.Xr). **Correction:** QTBUG-121781 is the still-open epic "Modernize iOS window management" (P2, fix version "Some future release", last updated 2026-08-14), not a visionOS ticket; the "Add preliminary support for Qt for visionOS" commit carries no task number, and the QWindow limitation it describes is what that epic tracks. JIRA does hold visionOS-specific XR tickets (contrary to the original "none found"): two P1 regressions fixed just before 6.12.0 (QTBUG-147559, QTBUG-150753), plus open items on passthrough (QTBUG-129736), a teleportation-example crash (QTBUG-134811), the Basic style (QTBUG-140488), and missing simulator-based CI (QTBUG-133524).

### Cited Findings
- **Original claim (two modes; transitions unsupported; Apple Silicon; no binary build; configure lines; Xcode not Qt Creator).** **Verdict: CONFIRMED verbatim** on the rendered 6.12.0 page, including the extra note "visionOS specific applications can also be placed in the low-immersion mode and will essentially work the same as an iPad/iOS application" and the deploy step "`qt-cmake -B … -S …` … produces an Xcode project that you can open in Xcode and deploy to the device." Nothing on the page addresses multi-scene/multiple windows, App Store, or limitations beyond the transition note. — [Getting Started With Apple Vision Pro](https://doc.qt.io/qt-6/qt3dxr-quick-start-guide-applevisionpro.html)
- **Original claim:** "Qt has a preliminary native visionOS port since 6.8 (added under QTBUG-121781)". **Verdict: CORRECTED.** QTBUG-121781 = "Modernize iOS window management", type Epic, status **Open**, resolution none, priority P2, fix version "Some future release", component "GUI: Window management", created 2024-02-01, updated 2026-08-14, one comment (2024-03-14, link to Apple's multi-window scenes doc). Description: "The Qt for iOS port was written when iOS didn't have support for advanced window management… we should modernize the way we do window management on iOS in Qt." — [QTBUG-121781 (JIRA REST)](https://bugreports.qt.io/browse/QTBUG-121781). The visionOS enablement commit "Add preliminary support for Qt for visionOS" (Tor Arne Vestbø, 2024-04-18) contains no `Task-number`; its message confirms the original quote: "Qt already runs on Vision Pro as 'Designed for iPad', using Qt for iOS… As our current window management approach on UIKit platforms depends on UIWindow and UIScreen there is currently no way to bring up QWindows. This will improve once we refactor our window management to use window scenes. To configure for visionOS, pass -platform macx-visionos-clang, and optionally add -sdk xrsimulator" — [code.qt.io commit d5bf42f7](https://code.qt.io/cgit/qt/qtbase.git/commit/?id=d5bf42f75b0ae35b7f02bb9211787ae1d44a98ba). Commits that do reference QTBUG-121781 are the 2024-03/04 "iOS: Decouple UIWindow management from QIOSScreen" series — [cgit log grep QTBUG-121781](https://code.qt.io/cgit/qt/qtbase.git/log/?qt=grep&q=QTBUG-121781)
- **New (precision):** visionOS builds of Qt must be **static**: "visionOS still requires static Qt builds, as the Swift entrypoint machinery has not yet been untangled." — commit "iOS: Enable building platform plugin as shared library" (2026-05-21, Qt 6.12 dev) — [code.qt.io commit 4fc36aa5](https://code.qt.io/cgit/qt/qtbase.git/commit/?id=4fc36aa558b7b79bdf1171cd49c22398e885b1dd). The immersive-space plumbing: "The QNativeInterface::QVisionOSApplication interface allows opening and dismissing an immersive space, as well as registering a compositor layer implementation that can be used to configure the compositor layer and render to it with Metal… All of this requires that the application follows the SwiftUI app lifecyle, so our application entrypoint is now a SwiftUI app." — commit "visionOS: Add support for immersive spaces" (2024-05-14) — [code.qt.io commit 1f667ba7](https://code.qt.io/cgit/qt/qtbase.git/commit/?id=1f667ba70e91563c2b508a70291fdac8a814c150)
- **Original gap:** "could not verify whether Qt's visionOS immersive space is opened as 'mixed' (passthrough) or 'full' style by default." **Verdict: partly resolved from primary sources.** Commit "visionOS: Change how the initial immersion style is set" (2025-02-13, picked to 6.9): "Set the initial style to be automatic, that's the default" (previously Qt's warning text showed the runtime style as 'full') — [code.qt.io commit 08146377](https://code.qt.io/cgit/qt/qtbase.git/commit/?id=08146377db8ce782bac5b9561338ba20f7101ac5).
