# OBS Studio frontend/control layer: architecture, external-UI pathways, and project direction

Scope: how the OBS Studio frontend is built, every viable way an external/"immersive" UI can control OBS and receive its preview/program video, and where the OBS project itself is heading (as of 2026-10-22). Primary source is the local checkout at `/home/user/obs-studio-immersive` (fork of obsproject/obs-studio; HEAD `7fc60ea` dated 2026-09-02, with later cherry-picks up to 2026-09-18; shallow clone of 54 commits, so no useful `git log` history). Local citations are given as `local: <path>`; the same files exist upstream at `https://github.com/obsproject/obs-studio/tree/master/<path>`.

Conventions: "Program" = the main output mix (`obs_render_main_texture`); "Preview" = the Studio-Mode preview scene drawn into the preview display; "display" = `obs_display_t`, a libobs swap chain bound to a native OS window.

## Key Question 1: How is the OBS frontend structured (Qt Widgets, QMainWindow, docks, OBSBasic, obs_display rendering into native windows, obs-frontend-api, events; what is in-process vs. separable)?

### Takeaway
The frontend is a single in-process Qt 6 **Widgets** application (`OBSApp : QApplication` → `OBSBasic : OBSMainWindow : QMainWindow`), built from `.ui` forms plus C++; there is no QML/Qt Quick anywhere in the tree. Preview/program video is rendered by libobs itself into a child native window (`QWidget::winId()` → `gs_window` → `obs_display_create`) on libobs's graphics thread; the Qt widget only owns the native surface. libobs (engine) and the Qt frontend are cleanly separable at build time (`ENABLE_FRONTEND` option) and the plugin-facing `obs-frontend-api` is a thin shared library whose 100+ functions forward to an in-process `OBSStudioAPI` object inside OBSBasic.

### Inferences
- The *engine* (libobs + graphics backend + plugins) is cleanly separable from the *UI*: everything the UI does to the engine goes through public `libobs` C API, and the UI-specific surface for plugins (`obs-frontend-api`) is a forwarding shim whose implementation is swappable (`obs_frontend_set_callbacks_internal`). A different frontend can therefore reuse libobs unchanged and optionally re-implement `obs_frontend_callbacks` so existing plugins keep working. (Based on `frontend/CMakeLists.txt`, `obs-frontend-api.cpp`, `docs/sphinx/frontends.rst`.)
- Preview video never passes through Qt: Qt only supplies a native child window handle; libobs draws into it on its own thread. Any UI toolkit that can hand libobs an `HWND`/`NSView*`/X11 window gets a preview for free; one that cannot (e.g. a remote headset) must receive frames by another route (see Q3/Q5).
- Because the whole OBS frontend is `QApplication`-based and in-process, a plugin runs on the same Qt event loop and GUI thread as OBSBasic, and may create additional top-level Qt windows (projectors already do), but it is bound to OBS's shipped Qt modules (Widgets/Svg/Xml/Network only).

## Key Question 3: What can an in-process plugin do via obs-frontend-api/libobs — control, docks, QMainWindow access, grabbing the program/preview texture every frame (zero-copy or readback), and could it host a Qt Quick 3D XR window?

### Takeaway
An in-process plugin has full control (scenes, transitions, studio mode/T-bar, streaming/recording/replay/virtualcam, profiles/collections, canvases, undo/redo, docks and menus, the `QMainWindow*`) and full GPU access: it can register its own `obs_display` on any native window, register a main-render callback, read `obs_get_main_texture()` and `gs_texture_get_obj()` (native `ID3D11Texture2D*`/`MTLTexture`/GL id), copy into a shareable texture (D3D11 shared handle; IOSurface-backed texture on macOS), or take CPU frames via `obs_add_raw_video_callback2`. Hosting a Qt Quick 3D XR window in-process is technically conceivable (same `QApplication`), but OBS does not ship Qt Quick, and Qt Quick 3D Xr is a technical preview whose visionOS mode is a standalone-app runtime, not a window inside a macOS process.

- Qt Quick 3D Xr: "Import Statement: import QtQuick3D.Xr. Since: Qt 6.8. - OBS bundles only `Qt::Widgets Qt::Svg Qt::Xml Qt::Network` (plus deps) — local: `frontend/cmake/ui-qt.cmake` (see Q1)

### Inferences
- **Per-frame program texture grab is straightforward in-process**: register `obs_add_main_render_callback` (or an `obs_display` draw callback), call `obs_get_main_texture()`, then `gs_copy_texture` into a plugin-owned texture. For zero-copy hand-off to another process: on Windows create the destination with a D3D11 shared handle (`gs_texture_get_shared_handle`); on macOS create an `IOSurface` yourself, wrap it with `gs_texture_create_from_iosurface`, copy into it each frame, and send the `IOSurfaceCreateMachPort`/XPC handle to the consumer — exactly the mac-virtualcam pattern. This works on both the OpenGL and Metal backends because both implement `device_texture_create_from_iosurface`.
- **Preview (Studio Mode) texture** is not a single engine texture: OBSBasic renders the preview scene directly into the preview display's swap chain via `obs_source_video_render` on the current preview scene. A plugin can replicate it by rendering `obs_frontend_get_current_preview_scene()` into its own render target with `gs_texrender`/`obs_source_video_render` each frame, or by using `obs_view`/`obs_canvas` to produce a second `video_t` and attaching an output/raw callback.
- **Hosting Qt Quick 3D Xr inside OBS** is not a realistic path to a headset: on visionOS the Xr runtime is a standalone app model (Tier One = "standalone on visionOS"), and on PCVR it targets OpenXR runtimes (Linux Tier Two). An in-process plugin could create a `QQuickView` on the desktop if it bundled matching Qt Quick libraries, but it would still render to a desktop window, not to the headset.

### Gaps
- No OBS documentation states thread-safety guarantees for calling `obs_get_main_texture()` outside the render callback; the frontend's own usage is only inside draw callbacks.
- Did not find an OBS- or plugin-sourced benchmark for `gs_stagesurface_map` readback cost at 1080p/4K.

## Key Question 4: obs-websocket v5 — capability coverage, limits (no video), bundled status, any video/WebRTC preview work

### Takeaway
obs-websocket 5.x (bundled with OBS since 28.0, default port 4455, rpcVersion 1, JSON or MsgPack over WebSocket, challenge/salt SHA-256 auth, request batches incl. frame-synced `SerialFrame`, bitmask event subscriptions) covers essentially every control surface including Studio Mode, T-bar, filters, scene items, outputs, media, hotkeys, stats, projectors and canvas-aware requests, but its only image path is `GetSourceScreenshot` (base64 JPEG/PNG etc., 8–4096 px, quality -1..100) — there is no video/frame stream and I found no accepted proposal for one.

### Cited Findings
- "obs-websocket is now included by default with OBS Studio 28.0.0 and above." "The 5.x server is a typical WebSocket server running by default on port 4455." — [obs-websocket README](https://github.com/obsproject/obs-websocket)
- In this tree obs-websocket is a git submodule at `plugins/obs-websocket` (`url = https://github.com/obsproject/obs-websocket.git`, pinned commit `e28f8497…`) — local: `.gitmodules`
- OBS 33 Beta 6: "Changed Safe Mode to not start WebSocket Server" (FiniteSingularity/RytoEX) — [33.0.0-beta6](https://github.com/obsproject/obs-studio/releases/tag/33.0.0-beta6)
- Protocol: "Current latest supported version is 1" (`rpcVersion`); subprotocols `obswebsocket.json` (default) and `obswebsocket.msgpack`; `Hello`(0)→`Identify`(1)→`Identified`(2), `Reidentify`(3); auth = base64(SHA256(base64(SHA256(password+salt))+challenge)); close code 4009 on failure — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)

- Outputs/Stream/Record: generic `GetOutputList/StartOutput/StopOutput/GetOutputSettings/SetOutputSettings`, `StartStream/StopStream/SendStreamCaption`, `StartRecord/StopRecord/PauseRecord/SplitRecordFile/CreateRecordChapter`, virtual cam and replay buffer controls; `GetStats` returns `cpuUsage, memoryUsage, availableDiskSpace, activeFps, averageFrameRenderTime, renderSkippedFrames, renderTotalFrames, outputSkippedFrames, outputTotalFrames, webSocketSession*Messages`; `GetVideoSettings` returns fps num/den and base/output size — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)
- Hotkeys: `GetHotkeyList`, `TriggerHotkeyByName(hotkeyName, contextName)` — docs say hotkey support is "as-is with no guarantee" — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)
- Scene items: `SetSceneItemTransform(sceneName|sceneUuid, sceneItemId, sceneItemTransform{…})`; Filters: full CRUD + index/enabled/settings; Inputs: volume (mul/dB), mute, audio sync offset, etc.; Media Inputs: status/cursor/offset/`TriggerMediaInputAction` — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)
- The protocol document "doesn't describe any video or frame streaming feature"; the only image facility is `GetSourceScreenshot` — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)

### Inferences
- For a headset UI, obs-websocket is the right **control + state** channel (it already mirrors the frontend API, including Studio Mode, T-bar and canvases, and is available from any language/OS including visionOS via a plain WebSocket). Video must come from a separate transport (Q5); screenshot polling is only suitable for thumbnails (each call encodes a full image on the OBS side and base64s it).

### Gaps
- No measured round-trip or per-call latency for `GetSourceScreenshot` was found in any source.
- No GitHub issue/PR proposing a binary frame channel or WebRTC preview in obs-websocket was found (searched the issue tracker summaries and the web); absence of evidence, not confirmed absence.

## Key Question 5: Low-latency preview video to a headset — options and realistic latency (NDI/DistroAV, WHIP/WebRTC, SRT/RIST, RTMP, Syphon/Metal shared textures, Apple mirroring) and what a visionOS app can consume

### Takeaway
Realistic transports, roughly in latency order: (1) same-machine GPU sharing (Spout on Windows / IOSurface on macOS — "no latency", but desktop-only); (2) WHIP/WebRTC from OBS's built-in `whip_output` (initial PR measured ~120 ms broadcaster→playback; third-party ~150 ms) consumable on visionOS via a WebRTC stack such as LiveKit's Swift SDK (visionOS 1.0+); (3) NDI via DistroAV (anecdotal 120–140 ms in one forum report; drift issues reported; NDI SDK exists for iOS, visionOS unconfirmed); (4) SRT/RIST (sub-second, buffer-dependent); (5) RTMP/HLS (2–5 s+). Apple's Mac Virtual Display is a screen mirror with no published latency figures.

### Cited Findings

**WHIP / WebRTC**
- OBS's WHIP PR: "With our initial measurements we see ~120 Milliseconds from Broadcaster to Playback. We believe we can continue to bring down this number as well." — [PR #7926](https://github.com/obsproject/obs-studio/pull/7926)
- A third-party guide: roughly 150 ms for WHIP vs RTMP "two to five seconds of latency baked in by design"; WHIP output shipped in OBS 30; "AV1 and HEVC support added shortly after and Simulcast added in 32.1.0"; "no major platform (Twitch, YouTube, Kick) accepts WHIP directly yet" — [obs-versions.com WHIP explainer](https://obs-versions.com/blog/obs-webrtc-whip-streaming)
- Dolby's goal for its OBS fork: "streaming in under half of a second from glass-to-glass" — [Dolby OptiView](https://optiview.dolby.com/?p=13518)
- VDO.Ninja: "the stock OBS build lacks the ability to perform NAT traversal" (they link a patched build); a buffer setting "can further help reduce any lost of skipped frames, but at the cost of increased latency" — [VDO.Ninja OBS WHIP guide](https://docs.vdo.ninja/guides/obs-whip-output-settings)
- OBS 31.0: "Restored STUN support for WHIP output" (mondain) — [31.0.0 release](https://github.com/obsproject/obs-studio/releases/tag/31.0.0)
- In-tree output: `whip_output` (see Q3) — local: `plugins/obs-webrtc/whip-output.cpp:745`
- visionOS consumption: LiveKit Swift SDK "supports all platforms including iOS, macOS, visionOS, tvOS, and Mac Catalyst" via SwiftPM (CocoaPods iOS/macOS only); FAQ lists visionOS 1.0+; a Swift Package Index visionOS build used LiveKit's WebRTC xcframework `150.7871.0-beta1` — [LiveKit installation (mirror)](https://www.mintlify.com/livekit/client-sdk-swift/installation), [LiveKit visionOS page (mirror)](https://mintlify.com/livekit/client-sdk-swift/platforms/visionos), [Swift Package Index build](https://swiftpackageindex.com/builds/21516A98-5C84-4005-9FAB-235C580E47D4)
- The popular stasel `WebRTC` xcframework has no visionOS slice: builds "Failed to build WebRTC … for visionOS" (Xcode 15.3 through 26.3 logs) — [Swift Package Index build logs](https://swiftpackageindex.com/builds/C952AB2E-BCF6-4781-89C7-92CD36926F26)
- WebKit/WKWebView: "from iOS 14.3, WKWebView has full support for WebRTC" (developer forum); Apple says Safari on Vision Pro uses the same WebKit engine; an unverified WebKit bug comment suggested visionOS could do 90 fps WebRTC video — [Apple Dev Forums](https://developer.apple.com/forums/thread/134216), [WebKit bug 272393](https://bugs.webkit.org/show_bug.cgi?id=272393)

**NDI / DistroAV**
- DistroAV (formerly OBS-NDI): NDI Source, NDI Output ("Transmit OBS video and audio to NDI"), NDI Filter/Dedicated Output; requires "OBS v31.1.1 or higher" and "NDI Runtime v6.3 or higher"; Windows/macOS/Linux — [DistroAV README](https://github.com/DistroAV/DistroAV)
- Wiki labels the NDI Output section "(OBS Program & Preview)" i.e. it can emit either feed; alpha output tested with NV12/Rec.709/Full and the receiver in "Normal (safe)" latency mode — [DistroAV wiki](https://github.com/DistroAV/DistroAV/wiki)
- Forum latency anecdotes (not official): "From OBS to ProPresenter to the projectors I'm seeing a latency of about 120-140ms"; another user saw ~250 ms start then ~2 s drift within 30 s (bug #502, source-timestamp sync mode); another measured ~40 ms drift per 10 min (~720 ms after 3 h) fixed by toggling sync mode; logs showing audio buffering stepping up to ~725 ms — [OBS forum DistroAV thread p.24](https://obsproject.com/forum/threads/distroav-network-audio-video-in-obs-studio-using-ndi%C2%AE-technology.69240/page-24)
- NDI SDK for iOS exists: KlakNDI README — "the iOS platform requires the SDK for building with Xcode. Please download and install the NDI SDK for iOS in advance of building." — [KlakNDI](https://github.com/keijiro/KlakNDI); NDI SDK page lists version 6.3.2 and free vs commercial licenses — [ndi.video developers](https://ndi.video/for-developers/)

**Same-machine GPU sharing / Syphon / Metal**
- Spout (Windows): "no latency, compression or computational overhead" (texture sharing) — [OBS forum Spout listing](https://obsproject.com/forum/resources/obs-spout-bi-directional-video-sharing-with-obs-studio-from-any-spout-program.1384)
- macOS: no Syphon server in OBS (Q3); IOSurface sharing primitives exist in both GL and Metal backends (`gs_texture_create_from_iosurface`, `gs_texture_rebind_iosurface`) and the mac-virtualcam plugin ships IOSurfaces across processes via Mach ports — local: `libobs/graphics/graphics.h:823-825`, `libobs-metal/metal-texture2d.swift:476-500`, `plugins/mac-virtualcam/src/obs-plugin/OBSDALMachServer.mm:131-141`
- Metal README on preview presentation: CAMetalLayer allows "at most 3 drawables 'in flight'"; "OBS Studio's maximum frame rate is limited to the operating system's screen refresh interval" if it waits on drawables, so the backend blits a separately rendered preview texture into a drawable in a display callback, which can produce "slow and 'choppy' frame rates if the refresh interval of the operating system and the interval at which OBS can finish rendering a preview are too misaligned" — local: `libobs-metal/README.md` ("The State Of Previews")

**SRT/RIST/RTMP**
- OBS routes SRT and RIST through `ffmpeg_mpegts_muxer` — local: `frontend/utility/BasicOutputHandler.cpp:209-210`
- RTMP "two to five seconds of latency baked in by design" — [obs-versions.com](https://obs-versions.com/blog/obs-webrtc-whip-streaming)

**Apple mirroring / headset baseline**
- Vision Pro passthrough photon-to-photon ≈ 11 ms (OptoFidelity; Apple states 12 ms); Quest 3 ≈ 35–40 ms — [MIXED](https://mixed-news.com/en/quest-3-vision-pro-passthrough-latency-measurement/); hand-tracking ≈ 128 ms (Road to VR estimate) — [Road to VR](https://roadtovr.com/apple-vision-pro-meta-quest-3-hand-tracking-latency-comparison/)
- No measured latency figure for Mac Virtual Display was found; one Apple forum user reports "noticeable lag" without numbers — [Apple discussions](https://discussions-kr-prz.apple.com/thread/255486240)
- ScreenCaptureKit (relevant only for the reverse direction and for platform parity notes): Apple's doc metadata lists availability macOS 12.3+, Mac Catalyst 18.2+, and **iOS/iPadOS/tvOS/visionOS 27.0+** — [Apple ScreenCaptureKit doc JSON](https://developer.apple.com/tutorials/data/documentation/screencapturekit.json)

### Inferences
- For a PC/Mac development phase, the lowest-latency, highest-quality preview for a *desktop-hosted* immersive UI is in-process GPU sharing (own `obs_display` or shared texture) — zero encode. The same code path cannot reach a headset; the headset phase needs an encoded transport. WHIP (built in, ~120–150 ms per the sources above, H.264/HEVC/AV1) is the best fit for visionOS because mature WebRTC stacks exist there (LiveKit), while NDI requires the NDI SDK (iOS available, visionOS unconfirmed) and a Wi-Fi link tolerant of ~100+ Mbit/s streams.
- Steam Frame / PCVR: the immersive UI runs on the PC, so a Spout/D3D11 shared-texture or in-process `obs_display` into a desktop window composited by the VR runtime is viable; no network hop needed (inference; Steam Frame specifics not researched here).
- Separate Program and Preview feeds for Studio Mode need two streams (two WHIP outputs or NDI Program + Preview), or a client-side composite of a single multiview feed.

### Gaps
- No glass-to-glass measurement of OBS WHIP→visionOS decode was found; figures above are broadcaster→player on desktops.
- NDI SDK support for visionOS: not confirmed either way (ndi.video/docs.ndi.video could not be fetched from this environment).
- Apple Mac Virtual Display latency: no measured number found.
- SRT/RIST latency figures for OBS specifically: none collected (generic sub-second expectations only).

## Key Question 6: Headless / multi-frontend — can libobs run without Qt; how do Streamlabs (obs-studio-node) and others embed libobs with a different UI?

### Takeaway
Yes: libobs plus all plugins build with `ENABLE_FRONTEND=OFF`, and the official docs describe exactly the init sequence a custom frontend must follow (`obs_startup → obs_reset_video → obs_reset_audio → load modules → obs_post_load_modules`). The closest "different UI, same engine" analog is Streamlabs' obs-studio-node: a separate C++ server executable hosting libobs behind an IPC socket, with an Electron client that passes a native window handle over IPC so the server can `obs_display_create` a child window inside the Electron UI.

### Inferences
- A new immersive frontend has three architecture choices, mirroring the evidence: (a) **plugin inside OBS** (fastest to build; reuses OBSBasic's scene-collection/profile/output management; constrained to Qt Widgets process); (b) **new frontend linking libobs directly** (the documented "Frontends" path; must re-implement scene collections/profiles/outputs persistence and, optionally, `obs_frontend_callbacks` for plugin compatibility); (c) **Streamlabs-style out-of-process server** (libobs in a helper process, UI anywhere; preview via native child window on the same machine, or via encoded stream remotely). Option (a) is the natural PC/Mac phase; (c) matches the later headset phase.
- The Streamlabs server's empty macOS branch in `nodeobs_display.cpp` implies their macOS preview is implemented elsewhere (likely an ObjC++ path); treat the Windows HWND-child technique as the documented one.

## Key Question 7: OBS project direction — frontend refactor status, Idian widgets, OBS 31/32/33 changes, roadmap, Qt policy, CMake/macOS presets, iOS buildability

### Takeaway

### Inferences
- The OBS team's stated direction is incremental: keep Qt Widgets, restructure into per-class files (done), introduce its own widget set (Idian) and new dialogs (add-source dialog in 32.2), evolve multi-canvas, and harden Metal. An immersive UI should not expect a QML/declarative OBS frontend to appear; it should treat OBS as (a) an engine (libobs) plus (b) a scene/profile manager exposed via frontend API/websocket.
- Porting libobs itself to visionOS would require replacing AppKit/Carbon/IOKit usage in `platform-cocoa.m`, `obs-cocoa.m`, `gl-cocoa.m` (OpenGL does not exist on visionOS at all), re-targeting the Metal backend's `NSView`/`CAMetalLayer` swap chain to `CAMetalLayer`/RealityKit textures, and dropping macOS-only plugins — a large effort with no upstream groundwork. The sanctioned near-term path is therefore "OBS stays on the Mac/PC; the headset is a remote UI."
- Because OBS 33 moves plugins to a `core` folder and new third-party locations, any plugin shipped for this project should target the 33.x loader layout (legacy locations work only until 34.0).
