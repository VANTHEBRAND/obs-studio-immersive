## KQ1. Which open/closed obs-websocket issues overlap with the headset client's gaps (property schemas, encoder/output settings, hotkeys, audio, multiview/projector, settings apply, collection import, transition editing, "expose more")?

### Takeaway
Every one of the client's gaps already has at least one open feature request on the tracker, most of them 2–6 years old with zero maintainer comments; the only gap-adjacent items that moved were ones a maintainer (tt2468) or a core-team-sponsored contributor (exeldro, for canvases) implemented themselves. There are 86 open issues labelled "Issue: Feature Request" (4 pages) and 23 open PRs, several of which add exactly the requests the client needs and have sat unreviewed for 1–3 years.

## KQ2. Have the maintainers written down what is in scope for core requests vs vendor requests, and is there an rpcVersion 2 / 5.x roadmap, project board or milestone?

### Takeaway
There is no written scope policy document, no project board, and no active milestone; the de-facto roadmap is tt2468's 2021 "obs-websocket v5.0.0 Request outline" Google Sheet plus the "Issue: Feature Request" label. The only explicit statements are (a) the protocol doc's definition that vendors exist so plugins can add custom requests/events with their own documentation, (b) tt2468's statements that heavy features (video streaming) are "out of the scope of obs-websocket," (c) PatTheMav's 2025 view that a remote-control client "should not futz around with canvases," and (d) tt2468's Feb 2026 statement that exposing non-main-canvas events requires "an RPC version bump" — i.e., rpcVersion 2 is acknowledged as the vehicle for breaking changes but has no date or plan.

### Cited Findings
- Protocol doc design goals (generated from source): "RPC versioning - Client and server negotiate the latest version of the obs-websocket protocol to communicate with."; `rpcVersion` "gets incremented on each **breaking change**"; `obsWebSocketVersion` "may be used as a soft feature level hint. For example, a new WebSocket request may only be available in a specific obs-websocket version or newer, but the rpcVersion will not be increased" — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)
- Every request and event in protocol.md still reads "Latest Supported RPC Version: `1`"; additions are tagged "Added in v5.0.0" (280), v5.1.0 (3), v5.3.0 (2), v5.4.0 (4), v5.5.0 (3), v5.6.0 (4), v5.7.0 (5); the doc defines 147 requests and 60 events in total — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md) (counts from local grep of the generated file)

## KQ5. Vendor-request API facts (header, protocol shape, limits) and which shipping plugins use it

### Takeaway
The vendor API is a stable, three-generation (API v1→v3) proc-handler shim: a plugin registers a vendor name in `obs_module_post_load()`, registers named requests with `obs_data_t*` in/out callbacks, and emits events; clients reach it through the single core request `CallVendorRequest {vendorName, requestType, requestData}` and the `VendorEvent` event (subscription `Vendors`). It is request/response only (no streaming), synchronous on obs-websocket's worker thread pool, and used in production by obs-browser (first-party), Advanced Scene Switcher, Aitum Vertical Canvas (21 requests), Aitum Stream Suite (32), StreamUP (66 incl. deprecated aliases), obs-source-record, obs-ptz, obs-downstream-keyer, obs-transition-table, obs-source-copy, obs-draw, obs-loudness-dock and others; DistroAV does not register a vendor.

### Cited Findings — header `lib/obs-websocket-api.h` (master, 2026-10-22)
- `#define OBS_WEBSOCKET_API_VERSION 3`; `typedef void *obs_websocket_vendor;`; `typedef void (*obs_websocket_request_callback_function)(obs_data_t *, obs_data_t *, void *);` (request data, response data, priv); `typedef void (*obs_websocket_event_callback_function)(uint64_t, const char *, const char *, void *);` (required intent, event type, event data JSON string, priv) — [raw header](https://raw.githubusercontent.com/obsproject/obs-websocket/master/lib/obs-websocket-api.h)
- `struct obs_websocket_request_response { unsigned int status_code; char *comment; char *response_data; }` — response_data is a JSON string "because obs_data_t cannot represent an array of objects without breaking the API" (per header comment) — [raw header](https://raw.githubusercontent.com/obsproject/obs-websocket/master/lib/obs-websocket-api.h)
- Functions (all `static inline`, implemented over `proc_handler_call` on the handler returned by proc `obs_websocket_api_get_ph`): `unsigned int obs_websocket_get_api_version(void)` (returns 1 if proc missing); `struct obs_websocket_request_response *obs_websocket_call_request(const char *request_type, obs_data_t *request_data)`; `void obs_websocket_request_response_free(...)`; `bool obs_websocket_register_event_callback(cb, void *priv)`; `bool obs_websocket_unregister_event_callback(cb, void *priv)`; `obs_websocket_vendor obs_websocket_register_vendor(const char *vendor_name)`; `bool obs_websocket_vendor_register_request(obs_websocket_vendor vendor, const char *request_type, obs_websocket_request_callback_function request_callback, void *priv_data)`; `bool obs_websocket_vendor_unregister_request(obs_websocket_vendor vendor, const char *request_type)`; `bool obs_websocket_vendor_emit_event(obs_websocket_vendor vendor, const char *event_name, obs_data_t *event_data)` ("Does not affect event_data refcount.") — [raw header](https://raw.githubusercontent.com/obsproject/obs-websocket/master/lib/obs-websocket-api.h)
- Header warning verbatim: `// ALWAYS CALL ONLY VIA `obs_module_post_load()` CALLBACK!` / `// Registers a new "vendor" (Example: obs-ndi)` — [raw header](https://raw.githubusercontent.com/obsproject/obs-websocket/master/lib/obs-websocket-api.h)
- Proc names registered server-side: `get_api_version`, `call_request`, `register_event_callback`, `unregister_event_callback`, `vendor_register(in string name, out ptr vendor)`, `vendor_request_register(in ptr vendor, in string type, in ptr callback, out bool success)`, `vendor_request_unregister`, `vendor_event_emit(in ptr vendor, in string type, in ptr data, out bool success)` — [src/WebSocketApi.cpp](https://github.com/obsproject/obs-websocket/blob/master/src/WebSocketApi.cpp)
- API version history (git): define added 2021-12-30 (v1 = vendors, shipped 5.0.0); 2022-05-10 "base, lib: Add ability to call obs-websocket requests via plugin API" (v2, `obs_websocket_call_request`); 2024-04-23 "lib: Implement obs-websocket event callback access" (v3, shipped 5.5.0 on 2024-06-07) — all by tt2468 — [commit history of lib/obs-websocket-api.h](https://github.com/obsproject/obs-websocket/commits/master/lib/obs-websocket-api.h)
- Server-side semantics: `PerformVendorRequest` looks up vendor then request under shared locks and invokes `cb.callback(requestData, responseData, cb.priv_data)` synchronously; duplicate vendor names and duplicate request types are rejected with a warning; `call_request` refuses until `_obsReady` — [src/WebSocketApi.cpp](https://github.com/obsproject/obs-websocket/blob/master/src/WebSocketApi.cpp)
- Incoming websocket messages are parsed and dispatched on a thread pool (`_threadPool.start(...)` in `onMessage`), so vendor callbacks run off the UI/graphics threads — [src/websocketserver/WebSocketServer.cpp](https://github.com/obsproject/obs-websocket/blob/master/src/websocketserver/WebSocketServer.cpp)
- PR #1331 (Feb 2026) "Handled json::null values when converting to obs_data_t, following an upstream OBS change" — i.e., request JSON → `obs_data_t` conversion is where nulls/arrays can be lossy — [#1331](https://github.com/obsproject/obs-websocket/pull/1331)

### Cited Findings — protocol shape
- `CallVendorRequest` (Complexity 3/5, RPC 1, added 5.0.0). Request fields: `vendorName` String, `requestType` String, `?requestData` Object (default `{}`). Response fields: `vendorName`, `requestType` (echoed), `responseData` Object ("{} if request does not provide any response data") — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md#callvendorrequest)
- `VendorEvent` (Complexity 3/5, added 5.0.0): data fields `vendorName`, `eventType` ("Vendor-provided event typedef"), `eventData` Object; requires `EventSubscription::Vendors`, one of the bit flags `(General | Config | Scenes | Inputs | Transitions | Filters | Outputs | SceneItems | MediaInputs | Vendors | Ui | Canvases)` — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md#vendorevent)
- Vendor requests participate in ordinary `RequestBatch` (OpCode 8) like any request; no separate vendor error codes beyond the generic RequestStatus set — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)
- No message-size or payload limit is stated in protocol.md (grep for "maximum|size|payload" finds only unrelated text) — [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)

### Cited Findings — who ships vendors

## KQ6. The practical path to upstreaming: contribution rules, protocol-doc generation, who merges, how long request-adding PRs take, recent merged request-adding PRs

### Takeaway
Contribution mechanics are light (wiki guidelines, 50/72 commits, doc comments → CI-regenerated protocol.md) but review capacity is the bottleneck: since 2024 essentially every commit is committed by tt2468 or RytoEX; tt2468 authors most new requests himself (64 of ~150 authored commits since 2024) and his review attention is sporadic; RytoEX merges but has said he is "not familiar enough with websockets" to review protocol PRs. Maintainer-authored or core-team-sponsored request PRs merge in days to weeks; outsider request PRs have median waits measured in years and several have never received a maintainer comment.

### Cited Findings — rules and tooling
- Contributing Guidelines (wiki): development on `master`; camelCase variables, MixedCaps methods; "Request and event names use MixedCaps… consistent with terms like `Get`, `Set`, `Get[x]List`, `Start[x]`, and `Toggle[x]`"; JSON fields camelCase reusing existing names (`sceneName`, `inputName`, `sourceName`, `sceneItemEnabled`); tabs; "New or updated requests and events must include documentation comments. These comments are used to generate the protocol specification document (`docs/generated/protocol.md`)"; response fields with no data due to invalid state are `null`, not omitted; commits follow 50/72 with scope prefix (example "Requests: Add GetSceneList"); never PR from fork `master`; use Draft PRs for discussion — [Contributing-Guidelines wiki](https://github.com/obsproject/obs-websocket/wiki/Contributing-Guidelines); [Contribute-Code wiki](https://github.com/obsproject/obs-websocket/wiki/Contribute-Code)
- Doc comment format for a request: description, then `@requestField [?]name | Type | description | restrictions | default`, `@responseField name | Type | description`, `@requestType`, `@complexity 1-5`, `@rpcVersion -1`, `@initialVersion`, `@category`, `@api requests` (events use `@dataField`, `@eventType`, `@eventSubscription`) — [docs/README.md](https://github.com/obsproject/obs-websocket/blob/master/docs/README.md)
- Pipeline: `docs/build_docs.sh` runs `npm install && npm run comments` (comments.js parses `src/**/*.{cpp,h}` with parse-comments → `work/comments.json`), then `python3 process_comments.py` → `generated/protocol.json` ("a machine-readable documentation format that can be used to create obs-websocket client libraries"), then `python3 generate_md.py` → `generated/protocol.md`; categories are a fixed `categoryOrder` list in generate_md.py (a new category such as Canvases required editing it) — [docs/build_docs.sh](https://github.com/obsproject/obs-websocket/blob/master/docs/build_docs.sh); [docs/README.md](https://github.com/obsproject/obs-websocket/blob/master/docs/README.md); [docs/docs/generate_md.py](https://github.com/obsproject/obs-websocket/blob/master/docs/docs/generate_md.py)
- CI: `.github/workflows/generate_docs.yml` runs on every push to `master` (ignoring `docs/generated/**`), executes `CI/generate-docs.sh`, and commits as "Github Actions" with message `docs(ci): Update generated docs - <sha> [skip ci]`; contributors therefore should not hand-edit protocol.md — [generate_docs.yml](https://github.com/obsproject/obs-websocket/blob/master/.github/workflows/generate_docs.yml); [CI/generate-docs.sh](https://github.com/obsproject/obs-websocket/blob/master/CI/generate-docs.sh)

### Inferences
- Realistic upstream timelines: a small, parity-style, non-breaking request (new getter/setter on an existing libobs object, UUID-addressed, documented with the comment format) can land within a release cycle *if* tt2468 engages — the three such cases (#1187, #1224, #1265) took 6–37 days; anything larger or conceptually new (screenshots of program, transition payloads, canvases, typed schemas) has taken 6 months to indefinitely, and the 2025–2026 pattern (RytoEX merges only what tt2468/Warchamp7/PatTheMav approve; tt2468 reviews in bursts around OBS releases) makes a multi-request "control parity" series unlikely to be reviewed as a unit.
- The most upstream-compatible strategy is dual-track: ship everything as vendor requests now (that is what StreamUP/Aitum do for the same gaps), and submit a few narrow, obviously-parity PRs upstream (e.g., per-scene-item show/hide transition already drafted in #1322, blend method in #1352, mono in #1350, a `GetInputPropertiesSchema` closing #1099/#1227) timed before an OBS release's feature freeze, UUID-first, with docs comments and a Python test script like contributors have supplied.
- Anything touching projectors, docks or multiview must start as an obs-frontend-api PR in obsproject/obs-studio (the "Requires OBS Changes" label and ideas #2185/#2752 show the missing primitives), not as an obs-websocket PR.
