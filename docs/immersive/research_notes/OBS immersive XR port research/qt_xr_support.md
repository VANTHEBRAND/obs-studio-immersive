## 1. Qt Quick 3D XR: versions, status, backends, platforms, APIs

### Takeaway
Qt Quick 3D XR (`import QtQuick3D.Xr`, library `Qt6Quick3DXr`) shipped as a Technology Preview in Qt 6.8 (Oct 2024) and **is still marked `\preliminary` (Technical Preview) in Qt 6.12 LTS (30 Sep 2026)** — it has never been promoted to a fully supported module. It has exactly two backends: an OpenXR backend (Android/Quest, Windows D3D11/D3D12/Vulkan, Linux Vulkan/OpenGL incl. Monado, and macOS Metal for the Meta XR Simulator) and a native visionOS backend built on CompositorServices + ARKit + Metal.

### Inferences
- Because the module is still `\preliminary` in 6.12 LTS, its API is explicitly outside Qt's source/binary compatibility promise; expect API churn between minors (e.g., `hand` → `controller` rename in 6.10, `multiViewRenderingEnabled` becoming read-only in 6.9).
- Qt 6.12 LTS is the sensible baseline for a new XR project in late 2026: it has the OpenXR 1.1.49 headers, the macOS Metal OpenXR backend, XrItem popup/menu support, and LTS lifetime; 6.8 LTS lacks all of those.
- Steam Frame / SteamVR is not mentioned anywhere in Qt's XR docs; the only Valve-related mention is "SteamVR OpenXR runtime" and "Steam Link VR" in the PCVR tested-configuration table (see §4).

### Gaps
- I could not fetch the rendered 6.12 "What's New"/module page to confirm the exact wording of the Tech Preview banner, but the `\preliminary` qdoc command in the 6.12 branch is definitive.
- No Qt roadmap statement about when (or whether) Qt Quick 3D XR leaves Technical Preview was found.

## 2. XrItem, hosting 2D Qt Quick / Qt Widgets in XR, officially recommended path

### Takeaway
`XrItem` (since 6.8) is a Node-derived rectangle with a real-world `width`/`height` that hosts exactly one Qt Quick `Item` (`contentItem`) and scales it; it supports any Qt Quick content including Qt Quick Controls, and since 6.11 Popups/Menus. **There is no mechanism to host Qt Widgets inside Qt Quick 3D or XR** — Qt's docs only ever describe Qt Quick items as 2D content in 3D; a widgets UI would have to be rasterised (`QWidget::grab()`/`render()`) into an image/texture with hand-rolled input synthesis, or rewritten in QML.

### Cited Findings
- **XrItem definition:** "A virtual surface in 3D space that can hold 2D user interface content. \since 6.8. The XrItem type is a Qt Quick 3D Node that represents a rectangle with width and height. It holds one Qt Quick Item, specified by contentItem, and scales it to fit. This gives a convenient way to take traditional 2D user interfaces and display them on a virtual surface that has a real world size. Any other children of the XrItem will be treated as normal children of a Node, and will not be scaled." Example: `XrItem { width: 100; height: 100; contentItem: Rectangle { width: 600; height: 600 } }` creates "a virtual surface that's 1 meter by 1 meter and with a content item that's 600 pixels by 600 pixels. **Note that the effect here is achieved by scaling the content item and not by rendering the content item at a higher resolution.**" Properties: `contentItem`, `pixelsPerUnit`, `manualPixelsPerUnit`, `width`, `height`, `color` (background), `automaticHeight`, `automaticWidth`. An XrItem must be a descendant of an XrView ("Could not find XrView for XrItem" warning otherwise). — [qquick3dxritem.cpp (6.11)](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/qquick3dxritem.cpp) (rendered: https://doc.qt.io/qt-6/qml-qtquick3d-xr-xritem.html)
- Qt's XR scene units are centimetres (1 unit = 1 cm): the visionOS backend converts ARKit metres with `* 100.0f` ("m -> cm") and the XrItem example equates 100 units to 1 m — [qquick3dxrinputmanager_visionos.mm L151](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/xr/quick3dxr/visionos/qquick3dxrinputmanager_visionos.mm); [qquick3dxritem.cpp](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/qquick3dxritem.cpp)
- **Popup/Menu support in XrItem added in 6.11** ("through dedicated QQuickOverlay") — [whatsnew611.qdoc](https://raw.githubusercontent.com/qt/qtdoc/6.12/doc/src/whatsnew/whatsnew611.qdoc). Inference: before 6.11, Qt Quick Controls popups (ComboBox dropdowns, Menus, Dialogs) inside an XrItem did not render on the panel.
- **Module index example** shows the intended pattern: a `Model { id: monitor }` with a child `XrItem { contentItem: ScreenContent {} }` sized to the monitor mesh — [qt3dxr.qdoc (6.12)](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr.qdoc) (rendered: https://doc.qt.io/qt-6/qt-quick-3d-xr.html)
- **Generic "2D content in 3D" page (Qt Quick 3D, not XR-specific):** two approaches — (a) 2D `Item` children of any `Node`/`Model` rendered "in-line with the rest of the 3D scene, in the same render pass" with all 3D transforms, "any Qt Quick content, including Qt Quick Controls, Shape, ShaderEffect, ParticleSystem, can be used this way"; (b) `Texture.sourceItem` to texture a mesh with Qt Quick content rendered "as an offscreen layer". The page mentions only Qt Quick items; Qt Widgets are not mentioned at all. — [qtquick3d-2d.qdoc (6.12)](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/qtquick3d-2d.qdoc) (rendered: https://doc.qt.io/qt-6/qtquick3d-2d.html)
- **Texture.sourceItem input caveat:** "Currently input events are forwarded to the Item used as a texture source only if the user is limited to interacting with one sourceItem instance at a time… it's best to use a separate 2D subscene instance for each Texture instance, if you expect to manipulate interactive items inside." Also: sharing a sourceItem Texture across multiple QQuickWindows "is going to fail" with the threaded render loop. "If the item is a texture provider, no additional texture is used." — [qquick3dtexture.cpp (6.12)](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/qquick3dtexture.cpp) (rendered: https://doc.qt.io/qt-6/qml-qtquick3d-texture.html)
- **Multiview constraint on custom 2D content:** "when developing custom materials (QSGMaterial, QSGMaterialShader) or writing shaders for ShaderEffect, and the intention is to use that 2D content within a VR/AR scene in a Qt Quick 3D Xr application, the custom content must be multiview-aware. see QSGMaterial::viewCount()"; built-in items (Rectangle, Image, Text) are already multiview compatible; multiview is on by default and can be disabled with `QT_QUICK3D_XR_DISABLE_MULTIVIEW` — [qt3dxr-multiview.qdoc (6.12)](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr-multiview.qdoc) (rendered: https://doc.qt.io/qt-6/qt3dxr-multiview.html)
- **Widgets in a 3D/XR scene:** Searches for official Qt guidance on hosting QWidget content inside Qt Quick 3D returned only the old Qt 3D (not Qt Quick 3D) `Scene2D`/`QQuickWidget` examples and forum threads; nothing for Qt Quick 3D or XR — [search results summary: doc.qt.io qt3d-widgets-scene3d-example, forum.qt.io threads](https://doc.qt.io/qt-5/qt3d-widgets-scene3d-example.html). Qt's RHI widget docs add a structural constraint: "A single widget window can only use one QRhi backend… If two QRhiWidget or QQuickWidget widgets in the window's widget hierarchy request different APIs, only one of them will function correctly." — [QRhiWidget docs (search snippet)](https://doc.qt.io/qtforpython-6/PySide6/QtWidgets/QRhiWidget.html)
- The existing OBS frontend is a Qt Widgets application (`frontend/`, `UI/obs-app.cpp` in this repo) — local tree at `/home/user/obs-studio-immersive`.

### Inferences
- The officially supported path for 2D UI in XR is **Qt Quick content inside `XrItem`** (or `Texture.sourceItem` for curved/arbitrary surfaces). For OBS this means the XR shell UI must be QML; the Qt Widgets `OBSBasic` window cannot be embedded as-is.
- A pragmatic bridge for legacy widget dialogs is possible but unsupported: render a hidden `QWidget` with `QWidget::render()`/`grab()` into a `QImage`, expose it via a `QQuickImageProvider` or a custom `QQuickItem` texture provider, and synthesise `QMouseEvent`s from XR ray hits with `QCoreApplication::sendEvent()`. It costs a CPU readback per frame, loses native text hinting at scale, and breaks keyboard focus, so it should be limited to rarely used settings dialogs.
- Because XrItem *scales* rather than re-rasterises its content, the panel's effective DPI is fixed by `contentItem` pixel size ÷ physical size; the app must choose a high `contentItem` pixel size (and large fonts) for legibility, see §6.

### Gaps
- No Qt document states a maximum recommended XrItem resolution or texture size; no performance figures for XrItem are published.
- I found no official Qt statement that QQuickWidget/QWidget embedding is *impossible* in XR, only an absence of any mechanism in docs and source.

## 3. Qt for visionOS: platform status, app modes, Metal, App Store, limitations/bugs

### Takeaway
Qt has a preliminary native visionOS port since 6.8 (added under QTBUG-121781) that is **source-build-only, Apple-Silicon-only, deployed via Xcode**, and whose only immersive path is Qt Quick 3D XR driving a CompositorServices layer; ordinary `QWindow`s cannot be shown natively on visionOS, so "2D" Qt apps on Vision Pro run as iPad-compatibility apps built with Qt for iOS. visionOS is not in Qt's supported-platform tiers, and I found no public QTBUG tickets specific to visionOS XR.

### Cited Findings
- **Two modes, per Qt's visionOS guide (identical in 6.11 and 6.12):** "low-immersion" apps "can be developed as any regular iPad/iOS application and deployed to visionOS, these applications run in windowed mode and look like a regular iPad application floating in your VR environment"; "high-immersion" apps "are developed using the visionOS SDK and are run in 'full screen' mode, meaning QtQuick3D takes complete control of the rendering, with some exceptions (Like pass-through video of the hands)." "**visionOS supports applications transitioning between these two states, but this is not supported by QtQuick3D.Xr.**" "Developing for visionOS requires Apple hardware with Apple Silicon." "**There is no binary build of Qt for visionOS. You will need to build Qt from source.**" Configure: `configure -qt-host-path … -platform macx-visionos-clang -sdk xrsimulator|xros -submodules qtquick3d`. "Unlike the iOS/iPad applications, visionOS applications are not deployed using Qt Creator, but instead using Xcode." — [qt3dxr-apple-vision-pro-quick-start.qdoc (6.12)](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr-apple-vision-pro-quick-start.qdoc) (rendered: https://doc.qt.io/qt-6/qt3dxr-quick-start-guide-applevisionpro.html)
- **Designed-for-iPad path already works:** Qt commit message: "Qt already runs on Vision Pro as 'Designed for iPad', using Qt for iOS"; the visionOS change (QTBUG-121781) adds "preliminary support for Qt for visionOS" and states "as our current window management approach on UIKit platforms depends on UIWindow and UIScreen there is currently no way to bring up QWindows. This will improve once we refactor our window management to use window scenes." — [code.qt.io qtbase ios platform commit log (search snippet)](https://code.qt.io/cgit/qt/qtbase.git/log/src/plugins/platforms/ios/qiosintegration.mm?showmsg=1)
- **Native interface exposed by Qt Gui on visionOS:** `QNativeInterface::QVisionOSApplication` with `ImmersiveSpaceCompositorLayer { configure(cp_layer_renderer_capabilities_t, cp_layer_renderer_configuration_t); render(cp_layer_renderer_t); handleSpatialEvents(const QJsonObject&) }`, `setImmersiveSpaceCompositorLayer()`, `openImmersiveSpace()`, `dismissImmersiveSpace()` — guarded by `Q_OS_VISIONOS` — [qguiapplication_platform.h (qtbase 6.12)](https://raw.githubusercontent.com/qt/qtbase/6.12/src/gui/kernel/qguiapplication_platform.h)

- **Passthrough on visionOS:** `setPassthroughEnabled()` logs "Changing passthrough is not supported at runtime on visionOS!" (passthrough mode is fixed at launch by the immersive-space style) — [qquick3dxrmanager_visionos.mm L800-804](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/xr/quick3dxr/visionos/qquick3dxrmanager_visionos.mm)

(Source comment: "these are native gestures like pinch click/drag coming from SwiftUI".)
- **Reference space fixed on visionOS:** always `ReferenceSpaceLocalFloor`; depth submission implicit; `fixedFoveation` ignored (eye-tracked dynamic foveation) — [qquick3dxrview.cpp](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/qquick3dxrview.cpp)
- **XrHandModel has no content on Vision Pro** (system overlays real hands); the `xr_touch` example "will not work on the Apple Vision Pro" — [qquick3dxrhandmodel.cpp](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/qquick3dxrhandmodel.cpp); [xr_touch example qdoc](https://raw.githubusercontent.com/qt/qtquick3d/6.12/examples/quick3d/xr_touch/doc/src/qtquick3d-examples-xrtouch.qdoc)
- **visionOS CMake note:** "CMakeLists.txt changes also apply to visionOS, where we include the MacOSXBundleInfo.plist.in file" — [qt3dxr.qdoc](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr.qdoc)
- **Not a tiered supported platform:** the qtdoc "Supported Platforms" page (6.12) lists iOS and macOS but contains no `visionOS`/`xros` entry at all — [supported-platforms.qdoc (qtdoc 6.12)](https://raw.githubusercontent.com/qt/qtdoc/6.12/doc/src/platforms/supported-platforms.qdoc). Qt 6.8 What's New called it "preliminary support for visionOS" — [whatsnew68 (search snippet)](https://doc.qt.io/qt-6/whatsnew68.html)
- **Bug tracker:** Searches for visionOS-specific Qt Quick 3D XR tickets on bugreports.qt.io returned nothing relevant; the only XR tickets surfaced were multiview-related (QTBUG-114769 umbrella, QTBUG-114770 GL multiview, QTBUG-125600 "Property to control multiview rendering") — [QTBUG-125600](https://bugreports.qt.io/browse/QTBUG-125600); [QTBUG-114770](https://bugreports.qt.io/browse/QTBUG-114770)
- App Store / Qt licensing: see §7.

### Inferences
- A Vision Pro build of an OBS XR shell therefore needs: a from-source Qt built with `-platform macx-visionos-clang` (plus every dependency OBS needs, cross-compiled for xros), an Xcode-generated project, and a QML-only UI; you cannot reuse the existing macOS Qt Widgets window on visionOS even in a floating panel because `QWindow` does not come up natively. The only way to get the existing widget UI on Vision Pro is the "Designed for iPad" Qt-for-iOS build, which is a completely separate, non-immersive app.
- Controllers are absent on visionOS by design; the input model is gaze+pinch (mapped by Qt to left-mouse events on XrItems and on pickable models) plus ARKit hand joints; `XrVirtualMouse` driven by an `XrController` in Aim pose should also work since the visionOS input manager fills Aim/Grip poses, but this is inferred from source, not documented.
- Because transitioning between windowed and immersive modes is unsupported by Qt, an OBS XR app on visionOS would be immersive-only; a SwiftUI launcher window is Apple's required entry point but Qt's docs do not describe customising it.

### Gaps
- Exact supported visionOS/Xcode versions were not retrievable (the doc's `visionOS_supported_versions` anchor points at the tested-headset list, not a version table).
- No public QTBUG items about visionOS XR were found; absence may reflect search-engine coverage rather than absence of bugs.
- I could not verify from a primary source whether Qt's visionOS immersive space is opened as "mixed" (passthrough) or "full" style by default.

## 4. OpenXR on desktop: SteamVR on Windows/Linux, macOS situation, Monado

### Takeaway
Qt explicitly tests PCVR against the **SteamVR OpenXR runtime** on Windows (Quest 3 wired, Air Link, Steam Link, Virtual Desktop) and HTC Vive on Linux, and 6.11 added Monado/Xlib/Wayland OpenGL support on Linux. **On macOS there is no consumer OpenXR runtime** (Valve ended SteamVR for macOS in 2020; Monado supports Linux/Android/Windows only); Qt's macOS Metal OpenXR backend (6.9+) exists solely to run the Meta XR Simulator, so a macOS "XR" build can only be a developer/simulator build or a flat-screen preview.

### Cited Findings
- **PCVR page (6.12):** PCVR apps "are developed and deployed as regular desktop Windows or Linux applications… they render into offscreen buffers via OpenXR and a 3D API such as Direct 3D or Vulkan." Tested configurations for Meta Quest 3: "Wired connection (USB-C), Oculus OpenXR runtime; Wired connection (USB-C), **SteamVR OpenXR runtime**; Wireless via AirLink, Oculus/SteamVR runtimes; **Wireless via SteamLink, SteamVR OpenXR runtime**; Wireless via Virtual Desktop, SteamVR OpenXR runtime; Virtual Desktop, VDXR runtime." Special: "**Meta XR Simulator (Windows and macOS)**". "Generally, Direct 3D 11, Direct 3D 12, and Vulkan can be expected to be supported by all OpenXR implementations on Windows. OpenGL support is rare and has not been tested by Qt with PCVR." "Using Direct 3D 11 is not recommended, since … Multiview Rendering [is] not supported with that API. Prefer Direct 3D 12." Runtime selection via `XR_RUNTIME_JSON` or the Windows registry `HKLM\SOFTWARE\Khronos\OpenXR\1\ActiveRuntime`. Passthrough/AR features are "not uncommon[ly]… not available in PCVR systems." — [qt3dxr-pcvr.qdoc (6.12)](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr-pcvr.qdoc) (rendered: https://doc.qt.io/qt-6/qt3dxr-pcvr.html)
- Linux: Tier Two "HTC Vive in PCVR mode (Linux)" — [supported platforms qdoc](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr-supported-platforms.qdoc); 6.11 "Added OpenGL desktop Linux support (Monado, Xlib, Wayland platforms)" — [whatsnew611.qdoc](https://raw.githubusercontent.com/qt/qtdoc/6.12/doc/src/whatsnew/whatsnew611.qdoc); Vulkan backend compiled wherever `QT_FEATURE_vulkan` — [openxr/CMakeLists.txt](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/xr/quick3dxr/openxr/CMakeLists.txt)
- **macOS:** Qt 6.9 "Added Metal backend for OpenXR to support running in Meta XR Simulator on macOS" — [whatsnew69.qdoc](https://raw.githubusercontent.com/qt/qtdoc/6.12/doc/src/whatsnew/whatsnew69.qdoc); CMake: `MACOS AND QT_FEATURE_metal` → `qopenxrgraphics_metal.mm`, comment "macOS AND Metal && OpenXR 1.1.40 or later"; OpenGL OpenXR backend is excluded on macOS (`NOT MACOS`) — [openxr/CMakeLists.txt](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/xr/quick3dxr/openxr/CMakeLists.txt)
- **SteamVR on macOS discontinued:** Valve ended macOS support for SteamVR in May 2020 "so our team can focus on Windows and Linux"; the Valve Index does not support macOS — [9to5Mac](https://9to5mac.com/2020/05/01/valves-steamvr-ends-support-for-macos/); [Engadget](https://www.engadget.com/valve-cancels-steamvr-support-macos-162443682.html)
- **Monado platform coverage:** official getting-started: Linux and Android, "a windows port is in progress"; a 2026 article says Linux, Windows, Android; neither mentions macOS. March 2026: Monado is the base for Google AndroidXR, NVIDIA CloudXR, Pico, Qualcomm Snapdragon Spaces, etc. — [Monado getting-started (gitlab.freedesktop.org)](https://gitlab.freedesktop.org/monado/webpage/-/blob/master/getting-started.md); [GamingOnLinux Mar 2026](https://gamingonlinux.com/2026/03/monado-becomes-the-open-source-foundation-for-various-openxr-vr-vendors)
- Apple provides no OpenXR runtime for visionOS or macOS; Qt's visionOS support is the "one non-OpenXR platform" — [supported platforms qdoc](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr-supported-platforms.qdoc)

### Inferences
- A Qt Quick 3D XR build of the OBS shell on Windows/Linux will run against SteamVR's OpenXR runtime without Qt-specific work; the recommended graphics API on Windows is D3D12 (or Vulkan) for multiview; on Linux Vulkan.
- A **macOS** target cannot be a real headset build with Qt (no runtime to talk to). Realistic macOS options: (a) a flat "desktop preview" of the same QML scene using `View3D` instead of `XrView`; (b) a developer build against the Meta XR Simulator on macOS (Qt-tested); (c) streaming-based approaches that bypass OpenXR entirely (e.g., the Mac renders and streams video to the headset) which Qt does not help with. Building a single codebase that swaps `XrView`↔`View3D` at the root is feasible because both are Qt Quick 3D viewports (inference from the XR docs' description of the entry point).

### Gaps
- No source confirms whether Qt's macOS Metal OpenXR backend has been tested with any runtime other than the Meta XR Simulator.
- Monado on macOS: no evidence of a port; treat as unavailable.

## 6. Rendering 2D Qt content as panels in XR: performance, resolution/DPI, legibility, input routing

### Takeaway
Qt provides `XrItem` (flat panels, auto pixels-per-unit scaling), `Texture.sourceItem` (any mesh incl. curved), `XrVirtualMouse` (ray → mouse events for controllers/hand aim pose, with buttons and scroll), `XrView.processTouch/setTouchpoint` (direct hand-tracked touch, XrItem or any pickable Model since 6.11), and on visionOS automatic gaze+pinch → mouse conversion. There is no Qt guidance on target panel resolution or text size; XrItem scales the content rather than supersampling, so DPI must be managed by the app.

### Cited Findings
- `XrItem` scaling semantics: `pixelsPerUnit` "determines how many pixels in the contentItem's 2D coordinate system will fit in one unit of the XrItem's 3D coordinate system. By default, this is calculated based on the [content item size]"; `manualPixelsPerUnit` overrides; "the effect here is achieved by scaling the content item and not by rendering the content item at a higher resolution" — [qquick3dxritem.cpp](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/qquick3dxritem.cpp)
- `xr_input` example: "We position the XrItem in three dimensions and set it to be 75 cm wide and 100 cm tall", content "automatically scaled so it fills the XrItem"; "To allow a 3D controller to interact with 2D content, we need to add an XrVirtualMouse to map between them" — [xr_input example qdoc](https://raw.githubusercontent.com/qt/qtquick3d/6.12/examples/quick3d/xr_input/doc/src/qtquick3d-examples-xrinput.qdoc) (rendered: https://doc.qt.io/qt-6/qtquick3d-xr-input-example.html)
- **XrVirtualMouse:** "Maps 3D controller input to mouse input in 2D items… Mouse events are generated for the position where the forward vector of the source node intersects with a 2D item." Properties: `source` (Node, normally an XrController), `view` (XrView), `enabled`, `leftMouseButton`/`rightMouseButton`/`middleMouseButton` (bool), `scrollWheelX/Y` (speed; scroll events generated by a timer with `scrollTimerInterval` default 30 ms, `scrollPixelDelta` default 15). Canonical usage binds `leftMouseButton: rightTrigger.pressed` where `rightTrigger` is an `XrInputAction` with `actionId: [TriggerPressed, TriggerValue]` (and the example adds `IndexFingerPinch` for hands) — [qquick3dxrvirtualmouse.cpp](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/qquick3dxrvirtualmouse.cpp) (rendered: https://doc.qt.io/qt-6/qml-qtquick3d-xr-xrvirtualmouse.html)
- **Direct touch:** `XrView.processTouch(position, pointId)` "will search for an XrItem, or a Model with a sourceItem texture, near position and send a virtual touch event… The return value is the offset between position and the touched point on the surface. This can be used to prevent a hand model from passing through an XrItem"; `setTouchpoint(target, position, pointId, pressed)` sends synthetic touch to an Item; `touchpointState(pointId)` returns a map (6.11: surface position and normal) — [qquick3dxrview.cpp](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/qquick3dxrview.cpp); `xr_advanced_touch` demonstrates "touch on curved displays and 3D model touch handling" in UV space — [xr_advanced_touch qdoc](https://raw.githubusercontent.com/qt/qtquick3d/6.12/examples/quick3d/xr_advanced_touch/doc/src/qtquick3d-examples-xradvancedtouch.qdoc)
- **visionOS gaze+pinch** is translated by Qt into left-button `QMouseEvent`s along the system `selectionRay` via `processPointerEventFromRay` (no app code needed) — [qquick3dxrinputmanager_visionos.mm](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/xr/quick3dxr/visionos/qquick3dxrinputmanager_visionos.mm)
- Pinch on OpenXR requires `XR_MSFT_hand_interaction` ("XrInputAction for pinch gestures") — [extensions qdoc](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr-supported-openxr-extensions.qdoc)
- Performance levers Qt documents: multiview (on by default, "expected to improve performance, reducing the GPU and especially the CPU load"), fixed foveation (`XrView.fixedFoveation`, default High on Quest), depth submission trade-offs (MSAA resolve cost, tiled-GPU store cost), 6.8 scene-graph work making "all standard Qt Quick items and materials… compatible with Multiview Rendering… utilized transparently… when 2D content is embedded into a Qt Quick 3D XR scene" — [qt3dxr-multiview.qdoc](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr-multiview.qdoc); [qquick3dxrview.cpp](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/qquick3dxrview.cpp); [whatsnew68.qdoc](https://raw.githubusercontent.com/qt/qtdoc/6.12/doc/src/whatsnew/whatsnew68.qdoc)
- Text/legibility: no Qt XR document gives DPI or font-size guidance (searched docs and examples; the only sizing statement is the 100-units-per-metre example above).

### Inferences
- Practical DPI formula for an OBS panel: pixels-per-unit = contentItem px ÷ XrItem cm; e.g., a 1 m-wide panel with a 2000 px-wide contentItem is 20 px/cm (~50 px/inch at panel scale) — at 1.5–2 m viewing distance this is roughly a 2560-wide monitor's angular density, so contentItems should be sized at least 2–3× the "logical" OBS layout and `Text` rendered with distance-field/native rendering; `Image`-based widget grabs will look blurrier than native Qt Quick text because they are scaled bitmaps.
- Interaction model for OBS: controller/hand-aim ray → `XrVirtualMouse` (gives real `QMouseEvent`s so existing Qt Quick Controls — buttons, sliders, list views, context menus (6.11+) — work unchanged); add `scrollWheelY` bound to a thumbstick for scene/source lists; on visionOS rely on Qt's built-in gaze+pinch mapping and keep targets ≥ 60 px because there is no hover before pinch.
- Keyboard entry inside XR panels has no Qt-provided solution; Qt Virtual Keyboard (GPLv3/commercial) is the obvious candidate but was not verified in XR.

### Gaps
- No published benchmark of XrItem/sourceItem panel cost on Quest 3 or Vision Pro.
- Whether `XrVirtualMouse` hover (MouseMove without button) is delivered on visionOS (gaze without pinch) is not evident from source; Qt only synthesises events while a pinch is active.

## 7. Live video onto 3D surfaces (OBS preview, NDI, WebRTC decoder) in Qt Quick 3D

### Takeaway
Qt Quick 3D can texture any surface with (a) any Qt Quick `Item` via `Texture.sourceItem` (zero extra copy if the item is a `QSGTextureProvider`), including Qt Multimedia's `VideoOutput`, or (b) a native GPU texture wrapped with `QNativeInterface::QSGMetalTexture/QSGVulkanTexture::fromNative()` exposed through a custom texture-provider item; Qt Multimedia's `QVideoFrame` can carry RHI texture handles (`RhiTextureHandle`) for GPU-decoded frames. Nothing Qt-specific exists for importing an OBS/libobs render texture — that needs a small custom `QQuickItem` texture provider wrapping the Metal/Vulkan/D3D texture OBS renders into.

### Cited Findings
- `Texture.sourceItem`: "allows any 2D Qt Quick content to be used as a texture source by rendering that item as an offscreen layer. **If the item is a texture provider, no additional texture is used.**" plus `autoOrientation` (sourceItem textures get an implicit V flip) and `textureProvider` property (added 6.7) — [qquick3dtexture.cpp (6.12)](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/qquick3dtexture.cpp); [Texture QML docs (search snippet, textureProvider since 6.7)](https://doc.qt.io/qt-6/qml-qtquick3d-texture.html)
- `VideoOutput` is "a visual component that can be embedded into a QQuickScene or Window", driven by `MediaPlayer`/`CaptureSession` via a `QVideoSink` — [Qt Multimedia Video Overview (search snippet)](https://doc.qt.io/qt-6/videooverview.html); its implementation `QQuickVideoOutput` in `src/multimediaquick/qquickvideooutput.cpp` ("Render video or camera viewfinder") — [qquickvideooutput.cpp (6.12)](https://raw.githubusercontent.com/qt/qtmultimedia/6.12/src/multimediaquick/qquickvideooutput.cpp). (A grep of that file shows no `isTextureProvider` override, so it is *not* a texture provider; sourceItem will render it to an offscreen layer — one extra GPU pass, no CPU copy.)
- `QVideoFrame` handle types include `RhiTextureHandle` and includes `<rhi/qrhi.h>`; `QVideoFrameFormat` has `Format_SamplerExternalOES` and `Format_SamplerRect` pixel formats for platform GPU textures — [qvideoframe.cpp (6.12)](https://raw.githubusercontent.com/qt/qtmultimedia/6.12/src/multimedia/video/qvideoframe.cpp); [qvideoframeformat.cpp](https://raw.githubusercontent.com/qt/qtmultimedia/6.12/src/multimedia/video/qvideoframeformat.cpp)
- Native texture import into the scene graph: `QNativeInterface::QSGMetalTexture::fromNative(id<MTLTexture>, QQuickWindow*, size, options)` — "The native object is wrapped, but not owned, by the resulting QSGTexture"; "currently suitable for 2D RGBA textures only"; must be called on the render thread after scene-graph init; Vulkan and D3D equivalents exist; examples "Scene Graph - Metal Texture Import" / "Vulkan Texture Import" — [QNativeInterface::QSGMetalTexture docs (search snippet)](https://doc.qt.io/qt-6/qnativeinterface-qsgmetaltexture.html); [Metal texture import example](https://doc.qt.io/qt-6/qtquick-scenegraph-metaltextureimport-example.html)
- `QQuickRhiItem` (Qt 6.7, tech preview): QRhi-based replacement for QQuickFramebufferObject rendering into an offscreen colour buffer, one codebase for Vulkan/Metal/D3D/OpenGL; rendering runs on the scene-graph render thread; not functional with the software backend — [QQuickRhiItem docs (search snippet)](https://doc.qt.io/qt-6/qquickrhiitem.html); [Scene Graph - RHI Texture Item example](https://doc.qt.io/qt-6.6/qtquick-scenegraph-rhitextureitem-example.html)
- Qt 6.8 QQuickRenderTarget additions aimed at XR: automatic multisample resolve, `setDepthTexture()`, texture view format override, and no longer invalidating on every `setRenderTarget()` call "because the texture comes from a buffer pool maintained by an external engine, framework, or XR compositor" — [whatsnew68.qdoc](https://raw.githubusercontent.com/qt/qtdoc/6.12/doc/src/whatsnew/whatsnew68.qdoc)
- Qt 6.9 QRhi: Vulkan wait/signal semaphore pass-through "allowing integration of external rendering/compute engines that rely on multiple threads and require appropriate synchronization with the scenegraph" — [whatsnew69.qdoc](https://raw.githubusercontent.com/qt/qtdoc/6.12/doc/src/whatsnew/whatsnew69.qdoc)
- OBS in this repo has `libobs-metal`, `libobs-d3d11`, `libobs-opengl` graphics backends — local tree `/home/user/obs-studio-immersive` (`ls` output). Qt XR on visionOS is Metal; on Windows D3D12/D3D11/Vulkan; on Linux Vulkan/OpenGL (§1).

### Inferences
- Lowest-latency path for the OBS program/preview: have libobs render into a texture on the **same** graphics device Qt's scene graph uses (Metal on visionOS/macOS — Qt's `QQuickGraphicsDevice` can share an existing `MTLDevice`; D3D12/Vulkan on Windows/Linux), wrap it with `QSGxxxTexture::fromNative()` inside a custom `QQuickItem` that implements `QSGTextureProvider`, and reference that item from `Texture.sourceItem` — the "if the item is a texture provider, no additional texture is used" clause makes this effectively zero-copy. Cross-API cases (libobs-d3d11 vs Qt d3d12) need a shared-handle or a copy.
- NDI/WebRTC decoders delivering `QVideoFrame`s can feed a `QVideoSink`→`VideoOutput`→`Texture.sourceItem` chain with one offscreen-layer pass; GPU-decoded frames stay on the GPU (`RhiTextureHandle`), CPU frames incur one upload. For 4K at 60 fps the extra layer pass is likely acceptable on PC but costly on Quest-class mobile GPUs (inference; no numbers).
- Multiview means the panel texture is sampled twice per frame but rendered once, so video panels do not double in cost under XR (per Qt's multiview description).

### Gaps
- No Qt example or doc demonstrates a `VideoOutput` directly as a `Texture.sourceItem`; functionally implied but untested here.
- Zero-copy GPU video frame → Quick 3D on Metal (visionOS) is not documented end-to-end; VideoToolbox-decoded `CVPixelBuffer` → Qt path details were not found.

## 8. Licensing: Qt Quick 3D / XR are GPLv3-or-commercial (not LGPL); impact on an OBS (GPLv2+) fork and the App Store

### Takeaway
**Qt Quick 3D and therefore Qt Quick 3D XR are not available under LGPL** — every source file is `LicenseRef-Qt-Commercial OR GPL-3.0-only`, and Qt's licensing page lists Qt Quick 3D among the GPLv3-only modules. OBS is "GPLv2 or any later version", so an OBS fork can lawfully combine with GPLv3 Qt Quick 3D by distributing the combined work under GPLv3, but any OBS plugin/source code that is GPLv2-*only* would be incompatible. For the App Store, GPL-licensed apps face Apple-terms conflicts and Qt's own page warns that store rules may conflict with (L)GPL; a commercial Qt licence is the conventional route and is a cost/contract decision, not a technical one.

### Cited Findings
- Source headers: `qquick3dviewport.cpp`, `qquick3dxrview.cpp`, `qquick3dxritem.cpp` (Qt Quick 3D and XR): `SPDX-License-Identifier: LicenseRef-Qt-Commercial OR GPL-3.0-only`; by contrast qtbase's `qwidget.cpp`: `LicenseRef-Qt-Commercial OR LGPL-3.0-only OR GPL-2.0-only OR GPL-3.0-only` — [qquick3dviewport.cpp (6.12)](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/qquick3dviewport.cpp); [qquick3dxrview.cpp (6.11)](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/qquick3dxrview.cpp); [qwidget.cpp (qtbase 6.12)](https://raw.githubusercontent.com/qt/qtbase/6.12/src/widgets/kernel/qwidget.cpp). The qtquick3d repo's `LICENSES/` directory contains `GPL-3.0-only.txt`, `LGPL-3.0-only.txt` (used only by some non-module files), `LicenseRef-Qt-Commercial.txt`, and no `GPL-2.0-only.txt` — [qtquick3d LICENSES listing probed via raw URLs](https://github.com/qt/qtquick3d/tree/6.12/LICENSES)

- OBS licence: `COPYING` is GPL v2 text; README: "distributed under the GNU General Public License v2 (or any later version)"; `libobs/obs.h` header: "either version 2 of the License, or (at your option) any later version" — local repo `/home/user/obs-studio-immersive/COPYING`, `README.rst`, `libobs/obs.h`. - GPL vs App Store: community/legal commentary holds that App Store terms impose "further restrictions" incompatible with GPLv2; the FSF and Qt mailing-list posts note cases where (L)GPL software was removed from the App Store at copyright-holder request, while other GPL apps remain — [Apple dev forums thread 4783](https://developer.apple.com/forums/thread/4783); [Qt interest list 2018](https://lists.qt-project.org/pipermail/interest/2018-March/029691.html). LGPLv3 on iOS is complicated by the relinking requirement; Qt's 2020 licensing slides say static linking is not OK under LGPLv3 unless users can relink — [Qt licensing webinar PDF (search snippet)](https://149513.fs1.hubspotusercontent-eu1.net/hubfs/149513/India%20Marketing%20Assets/webinar%20recording/202005-Qt%20Virtual%20Tech%20Conf_Qt%20Licensing%20Explained.pdf); [wiki.qt.io Licensing-talk-about-mobile-platforms](https://wiki.qt.io/Licensing-talk-about-mobile-platforms)

### Inferences
- Technical licence math: OBS core (GPLv2-or-later) + Qt Quick 3D/XR (GPLv3-only) ⇒ the combined XR app must be distributed under **GPLv3**. Any bundled OBS plugin whose licence is GPLv2-*only* (several third-party plugins are) cannot be shipped in the same binary. The existing OBS widgets UI only needs LGPL Qt modules, which is why upstream OBS has no such constraint today.
- For the Apple App Store specifically, shipping a GPLv3 app is legally contentious and historically fragile; the realistic options are (1) a commercial Qt licence for the XR build (also removes the LGPL relinking question for iOS/visionOS static builds), or (2) TestFlight/enterprise/side-loading distribution outside the public store, or (3) not using Qt Quick 3D at all for the visionOS build. This is a decision the report should flag for legal review; nothing here is legal advice.
- Commercial Qt licensing has no per-app-store caveat but is per-developer-seat and would apply to every contributor building the XR target — a significant friction for an open-source fork.

### Gaps
- I did not find Apple's current, authoritative position on GPLv3 apps in the App Store (only forum/mailing-list evidence).
- Commercial Qt pricing for 2026 was not researched.

## 10. Realistic architecture for a Qt-based OBS XR app (synthesis for the report writer)

### Takeaway
A Qt-based immersive OBS has to be a **new QML/Qt Quick 3D XR front-end process or mode** that talks to libobs (and/or a remote OBS via obs-websocket/NDI/WebRTC), rather than a port of the Qt Widgets `OBSBasic` UI. Target matrix: visionOS = native source-built Qt 6.12 + visionOS backend (immersive-only, gaze+pinch, GPLv3-or-commercial Qt); Windows/Linux PC = OpenXR via SteamVR runtime (Steam Frame in PCVR mode, D3D12/Vulkan, controllers + hands); macOS = flat preview (`View3D`) or Meta XR Simulator only.

### Cited Findings
- Entry-point difference: "The entry point in an Qt Quick 3D Xr application is not a View3D but the XrView. In addition, an XrOrigin defines the scene's origin"; scene units must match real-world units — [qt3dxr.qdoc](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr.qdoc)
- Backend is selected at Qt build time (visionOS vs OpenXR), so the same application source builds for both with different Qt builds — [CMakeLists.txt](https://raw.githubusercontent.com/qt/qtquick3d/6.11/src/xr/quick3dxr/CMakeLists.txt)
- Qt's advice for dual-mode devices: "Use PCVR (or even the Meta XR Simulator) during development when it makes sense, but focus on the standalone (Android) build for AR features and for final delivery" — [qt3dxr-pcvr.qdoc](https://raw.githubusercontent.com/qt/qtquick3d/6.12/src/quick3d/doc/src/xr/qt3dxr-pcvr.qdoc)
- All other supporting facts are cited in §§1–9.

### Inferences
- **Layering:** (1) libobs / obs-frontend-api core (GPLv2+) unchanged; (2) a thin C++ bridge exposing scenes/sources/mixer/preview textures as `QObject`/`QAbstractItemModel`s plus a `QQuickItem` texture provider for program/preview; (3) a QML XR shell: `XrView` → `XrOrigin` (XrController ×2, XrHandModel ×2 for OpenXR) → scene with `XrItem` panels (scene list, sources, mixer, controls) and `Model`+`Texture.sourceItem` video walls; `XrVirtualMouse` per hand for OpenXR; visionOS relies on built-in gaze+pinch; (4) a platform shim that swaps `XrView` for `View3D` on macOS/desktop preview.
- **Why not reuse widgets:** no QWidget hosting in Quick 3D; `QWindow` cannot appear natively on visionOS; and a widgets window on PCVR would appear on the desktop monitor, not in the headset.
- **Licensing fork in the road** (§8) is the single biggest non-technical blocker for the visionOS App Store goal and should be decided before investing in the Qt route; an alternative for visionOS only (SwiftUI/RealityKit shell + libobs or remote OBS) sidesteps both the GPLv3 and the from-source Qt build issues but forfeits code sharing with the OpenXR targets.

### Gaps
- No empirical data on frame-time budgets for Qt Quick 3D XR on Quest 3/Vision Pro with large interactive XrItems; prototype measurement is required.
